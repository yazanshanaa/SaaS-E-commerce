# A2 — Storefront and template engine

Implementation decisions taken while building the public surface. Folded into
`docs/DECISIONS.md` during the Group A merge review.

---

## The rendering pipeline

- **`src/templates` is a library; `src/app/site` is the only thing that touches the database.**
  The section components take a plain view model (`src/templates/view-model.ts`), never a Prisma
  row. That is what lets B2 build a live appearance preview against the same components without
  a second data path, and it is what makes the whole renderer unit-testable.
- **`src/app/site/_data` is a PRIVATE folder, not a route.** App Router ignores an
  underscore-prefixed segment, so the loader, the metadata builder and the consent helpers sit
  beside the pages that use them instead of in a `src/server/storefront` folder A2 does not own.
- **The template chooses MARKUP, not just CSS.** `TemplateLayout` picks a hero shape, a product
  card shape and a categories shape per template, and the components branch on it. "Three
  palettes over one layout" is the failure mode CLAUDE.md's design rules exist to prevent, and a
  token set alone cannot prevent it. `tests/unit/a2-templates.test.ts` asserts all three
  structural choices differ.
- **Section configs are re-parsed at the render boundary.** The loader already normalises them;
  the renderer parses again so each component receives a TYPED config, and so a config written
  by an older dashboard renders with today's defaults instead of `undefined`.
- **An unknown stored `templateKey` falls back to `diwan` rather than throwing.**
  `templates_allowed` is enforced where the key is WRITTEN (A1 onboarding, B2 appearance).
  Refusing to render at read time would take a paying merchant's site down over a data-migration
  mistake.

## Colour, contrast and tokens

- **`resolveColors()` from `site-contract` is called, never reimplemented** — the same function
  A1 and B2 call when they WRITE a theme, so what renders is what the merchant was shown,
  contrast adjustments included. Both modes (`preset` and `custom`) go through it.
- **Four colours are DERIVED at render time and guarded again**: `onPrimary`, `onSecondary`,
  `textMuted` and a new `link` token. A brand accent only has to clear 3:1 to be a button fill;
  the same colour as a *sentence* needs 4.5:1, and that gap is the most common contrast defect
  in a themed site.
- **Muted text and links are guarded against all THREE surfaces** — background, card surface and
  the footer's `surfaceAlt`. Guarding only against the background is how a palette passes review
  and then fails the audit on the footer heading; that is precisely what the axe run caught, and
  the unit test now asserts all three.
- **A theme row that no longer parses falls back to the template defaults.** Throwing would take
  a live storefront down over a cosmetic value.

## CSS

- **Four plain `.css` files, imported once in the surface layout.** Next bundles them into one
  cached stylesheet, so this is a single request rather than four, and every template's rules are
  namespaced under its own `[data-template]`. The alternative considered — inlining the active
  template's CSS into each document — repeats the same bytes on every page view and can never be
  cached.
- **Tenant colours are an inline `style` of `--t-*` custom properties on the root element.**
  Colour customisation therefore writes tokens only: there is no per-tenant stylesheet to
  generate, cache or invalidate, and no path by which a colour picker can produce a CSS rule.
- **`:where(.sf-root a) { color: inherit }`, not `.sf-root a { … }`.** The plain form scores
  (0,1,1) and silently beats `.sf-btn` at (0,1,0), so every button label inherited the body text
  colour over a filled brand background. It shipped, axe caught it, and `:where()` — zero
  specificity — is the fix. Worth remembering as a class of bug: a cascade accident that looks
  harmless in review and only shows up in a contrast checker.
- **Logical properties only.** A unit test greps all four stylesheets for physical
  `left`/`right`/`margin-left`… and fails on any of them (invariant 6).

## Fonts

- Arabic-subset woff2 only, self-hosted under `public/fonts/<family>/`, `font-display: swap`,
  and **one preload hint per page — the active template's regular weight**. All three families'
  `@font-face` rules are in the bundle (a browser fetches a font only when text matches it), but
  preloading three would spend the Fast 3G budget on two nobody will see.
- A unit test asserts every declared file exists, is under 120KB (an unsubset family is five
  times that), declares `swap`, and points at a local path rather than a CDN.

## Analytics and consent

- **`analyticsDecision()` is one pure function and the whole compliance surface.** Both gates —
  `can(tenantId,'analytics')` AND a stored consent record — resolve before it, and the Umami tag
  is only in the HTML when it returns `load: true`. There is no script on the page for a flag to
  switch on later, which is why "zero tracking before consent" is testable as bytes on the wire.
- **The consent banner is not shown on a plan without analytics.** Asking permission for
  something that can never happen is a dark pattern in the other direction.
- **Two records per decision, on purpose**: an HttpOnly cookie the server reads on the next
  request (so no database read per page view) and a `Consent` row per tenant with a timestamp
  (the compliance artefact Phase 6 reviews). The visitor hash is an HMAC over tenant + IP + user
  agent + MONTH, so it genuinely rotates and is not joinable across tenants.
- **`POST /api/storefront/consent` records nothing for a tenant without the feature.** A consent
  log for tracking that can never happen would make the أساسي claim harder to defend, not easier.

## Sections and site-level elements

- **Scheduling is applied in the LOADER, never in a component.** A bar or an offer card outside
  its window is never fetched, so next month's price is not in the page source of a site anyone
  can view-source. Hiding it with CSS would leave the merchant honouring an offer they had not
  launched.
- **The announcement bar's dismissal key is a hash of its own content.** Dismissing this week's
  bar must not swallow next week's — the classic form of this bug is a merchant certain the bar
  is broken because one visitor closed a different message a month ago.
- **Zero social links renders NOTHING, and the contact column carries the footer.** Every demo
  and every new account has none, so the empty case is the common case; an empty "تابعنا"
  heading over blank space is what looks broken.
- **The map section has no embedded iframe.** An embed is a third-party request that fires on
  first paint, before the visitor has answered the consent banner, on a page whose entire
  compliance claim is that nothing third-party loads until they have. Two deep links do the job.
- **The map fallback chain is coordinates → `config.query` → `Site.mapQuery` → `Site.address`.**
  The demo packs ship address text and no coordinates, so without it every demo renders a dead
  map on the day it is shown to a customer.
- **WhatsApp ordering composes the message client-side from a server-rendered template.**
  Everything except `{qty}` is substituted on the server, so the client component never imports
  the message catalogue (which would pull all seven namespaces into the storefront bundle) and
  the Arabic copy stays where the language gate can see it. No order row, no name, no phone (Q5).
- **A local WhatsApp number is REFUSED rather than guessed.** Bartaa sits in the Seam Zone:
  `059…` could be +970 or +972, and a wrong country code sends a customer's order to a stranger.
  The UI shows the phone number instead. The dashboard already demands international format.

## Default arrangement

A tenant is created with a `Site` row and no `Page`/`Section` rows — true of the Phase 1 seed's
demo tenant and of every account on the day A1 opens it. The renderer composes a **content-aware
default arrangement** (`buildDefaultSections`): hero first, then only the blocks that have
something behind them. Stored sections win outright; the two never merge.

## Legal footer — the Phase 6 contract

`src/templates/lib/legal.ts` owns the list: four pages always, plus the returns policy and the
permanent **"إلغاء معاملة"** link once `Site.sellingEnabled`. They all route through
`/p/{slug}`, which renders a `Page` row and its sections through the ordinary section renderer.

**Phase 6's whole job on the storefront side is to write those rows.** No template file changes,
no route is added. Until the rows exist, a known legal slug renders a short Arabic "قيد التجهيز"
page, noindex — a footer link that a compliance requirement forces onto every page must not lead
to a 404. Any other unknown slug still 404s.

## SEO

- Baseline metadata, sitemap, robots and product JSON-LD ship on **every plan**. Nothing in
  `_data/metadata.ts` asks what plan a tenant is on. `seo_tools` gates the editable
  title/description UI B2 builds — i.e. the WRITE — and `Site.metaTitle` / `metaDescription`
  simply override the derived values when present. A merchant downgraded from احترافي keeps the
  title they already wrote rather than watching their search result change overnight.
- Structured data is withheld from demo and suspended sites: a rich snippet is the artefact that
  survives longest after a page stops being crawlable.
- `sitemap.xml` lists the legal pages even before Phase 6 writes their rows, because the footer
  links to them from every page and a sitemap that omitted them would describe a different site.

## Caching

- The data read is one `unstable_cache` unit **keyed by tenantId**, tagged `storefront:{id}`,
  with a 300s TTL as a net. `revalidateStorefront(tenantId)` in `src/app/site/_data/cache.ts` is
  the contract other tracks call after any write that changes what the storefront renders.
- **Not keyed by hostname**, deliberately: a tenant answers on `{slug}.{DOMAIN}` *and* on a
  custom domain with identical content, so a hostname key would store the catalogue twice, halve
  the hit rate, and make an edit look applied on one hostname and stale on the other. The
  hostname→tenant map is a separate cache in `src/server/tenancy`, already invalidated on every
  Domain change — between the two, reassigning a domain is correct by construction.
- Redis is not involved. This is Next's own data cache, so a machine without Redis behaves
  identically to production.

## Capability visibility

The storefront honours `isCapabilityVisible()` for `announcement_bar`, `social_links`,
`announcements_board` and `map_location` (content that disappears when an admin hides it) and for
`colors` (hidden ⇒ the template's own palette). `sections_layout` is deliberately NOT consulted:
it governs who may REORDER sections, not whether they render.

`isCapabilityVisible()` is **fail-closed** — a missing `PlanCapability` row reads as hidden.
`prisma/seed.ts` writes all six rows for all four plans, so production is unaffected, but see
"For the merge reviewer" below.

## Performance — and what is NOT claimed

Built to the documented budget (LCP < 2.5s on Fast 3G, CLS < 0.1) and the mechanical proxies are
asserted in `tests/e2e/a2-storefront.spec.ts`:

- one preloaded, subset, self-hosted font per page and no CDN,
- **zero cross-origin requests before consent** — measured by counting the browser's requests,
- every `<img>` carries explicit `width` and `height`; `.sf-media` reserves the box with
  `aspect-ratio` before a byte arrives,
- only the first grid row is eager; everything below the fold lazy-loads,
- images resolve to generated CDN variants only, and an unaddressable image degrades to the
  template's deliberate no-image state rather than 500ing the page.

**The Lighthouse number itself is deferred to Phase 7.** Lighthouse is not installed and adding
it would be a `package.json` change, which is forbidden from a worktree. Phase 7 has the browser
tooling and the CI job; the documented gate ("mobile performance ≥ 90 with 30 products") is
recorded there, not claimed here.

## Sync points raised

1. **`X-Robots-Tag` on the HTML document of a demo or suspended storefront.** Two of the three
   noindex layers are complete and tested — the `robots` meta tag and the per-hostname
   `robots.txt`, which also carries the header — and `sitemap.xml` 404s with the header. The
   third layer, the header on the HTML response itself, cannot be set from `src/app`: Next 16
   gives a Server Component no way to write a response header, so it has to come from `proxy.ts`
   or `next.config.ts`, both forbidden. `proxy.ts` already knows `tenant.isDemo` and
   `tenant.isSuspended`; the fix is one line on the storefront branch:

   ```ts
   const response = intoSurface(request, headers, 'storefront');
   if (tenant.isDemo || tenant.isSuspended) {
     response.headers.set('x-robots-tag', 'noindex, nofollow');
   }
   ```

2. **There is no `custom_html` feature key.** `src/shared/features.ts` is frozen, so the section
   is gated on `seo_tools` — the other احترافي-only key that lets a merchant put raw content into
   the document — via a single constant, `CUSTOM_HTML_FEATURE_KEY` in
   `src/templates/lib/custom-html-gate.ts`. It fails CLOSED: أساسي and متجر cannot render raw
   HTML at all. When a real key is added, change that constant and nothing else.

3. **The `custom_html` sanitiser is hand-written** because a dependency cannot be added from a
   worktree. It is an allow-list tokeniser with an attack-list test file, and it is conservative,
   but Phase 6's hardening pass should replace it with a vetted library and keep the tests.

## For the merge reviewer

- **A plan created outside `prisma/seed.ts` must carry all six `PlanCapability` rows.** A1's plan
  CRUD is the place this could go wrong: a plan with no capability rows produces storefronts with
  no announcement bar, no offers board, no social links and no map, silently, because
  `isCapabilityVisible()` is fail-closed. Worth a default in A1's create path or a seed helper.
- `src/app/site/_data/context.ts` exports `loadTenantData` (the uncached read) purely so the
  integration suite can exercise it — `unstable_cache` needs a Next request scope. Production
  traffic always goes through the cached wrapper.
- The language gate's JSX heuristic reads `=> expression` followed by a JSX tag as a text node.
  Two call sites use a block-bodied arrow to avoid it (`src/app/site/page.tsx`,
  `src/app/site/products/page.tsx`). Noted so nobody "tidies" them back.
