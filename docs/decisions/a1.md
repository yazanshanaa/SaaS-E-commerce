# A1 — Super Admin panel

Decisions taken while building `src/app/admin`, `src/app/api/admin` and `src/server/admin`.
Folded into `docs/DECISIONS.md` at merge.

---

## The revenue rule, stated once and in three numbers

`docs/PHASES.md` requires the rule to be explicit in the UI *and* here, because "monthly
revenue" has three defensible meanings and choosing silently between them is how a platform
ends up with two figures that disagree and nobody able to say which is wrong. The overview shows
all three, labelled, plus a fourth forward-looking one:

- **الإيراد الشهري المتكرر** — forward-looking. Sum over ACTIVE subscriptions of the plan price,
  with yearly divided by twelve. "What does this book bill this month if nothing changes."
  Excludes the hidden demo plan — by `Plan.hidden`, never by plan name (invariant 2).
- **المتكرر المستحق هذا الشهر** — backward-looking, from `subscription` payments only. A monthly
  payment lands whole in its own month; a yearly payment contributes a twelfth to each of the
  twelve months beginning with the one it was paid in.
- **رسوم تأسيس وطلبات إضافية** — `setup_fee` and `change_request_addon`, on their own line, never
  in any recurring figure. A ₪350 setup fee counted as recurring makes month one look like a
  step change that never repeats.
- **المحصَّل هذا الشهر** — every kind together, inside the month. This is the number that
  reconciles against a bank statement, and it is deliberately NOT the recurring figure.

**Amortisation reads the subscription's CURRENT `billingPeriod`,** because a `Payment` row does
not record the period it bought. Switching a live subscription from yearly to monthly therefore
re-reads its history as monthly. The alternative — a period column on every payment — is a schema
change, and schema changes do not happen in a track. The functions are pure and pinned by
`tests/unit/a1-revenue.test.ts`.

## Impersonation crosses a hostname, so it crosses in two steps

Session cookies are host-only: `crossSubDomainCookies` is disabled (Phase 1) so a session can
never follow a visitor onto a merchant storefront. The consequence is that an impersonation
started on `admin.{DOMAIN}` sets its cookies on `admin.{DOMAIN}` — where the merchant dashboard
is not. Loosening the cookie scope would fix the symptom by handing every storefront a readable
session cookie; that is not a trade worth making for a support tool.

So the impersonated session is **minted on the admin host**, where the super admin's session
proves they may do it, and **replayed on the app host**, where the dashboard lives:

1. `startImpersonation` calls better-auth with the admin's own cookies and captures the
   `Set-Cookie` headers it produced — **both** of them: the new merchant session AND the
   `admin_session` cookie better-auth stores so `stopImpersonating` can restore the admin.
   Replaying only the first would strand the admin inside the merchant account with no way out.
2. Those headers are parked under a single-use, 60-second handoff token in `verifications` (a
   table only the auth context can read) and the browser is redirected to the app host carrying
   the token and nothing else.
3. `GET /api/admin/impersonation/consume` — reachable on `app.{DOMAIN}` because `/api/**` is
   unprefixed — deletes the record BEFORE trusting it, replays the cookies on its own response,
   and lands on the dashboard.

The admin's own session cookie is never moved or copied. The value in flight is a merchant
session that expires in an hour and is fully attributed by `impersonatedBy`. The `Domain`
attribute is stripped on replay so the cookies scope to whichever host serves them.

Both sides are audited: a tenant-owned row (who was impersonated) and a platform row (which
survives the tenant, because a demo is deleted when it closes and the sales tour that happened
on it should not be).

**Handoff to B2:** the dashboard must render the impersonation banner — the copy already exists
as `admin.impersonation.banner` and `admin.impersonation.exit` — and point its exit control at
`POST /api/admin/impersonation/stop`, which A1 ships. A1 cannot render it: `src/app/dashboard`
is B2's folder.

## Account creation

- **The owner is created without a credential account.** `resetPassword` creates the credential
  row the first time the merchant sets a password, so the only way into a merchant account is a
  link sent to an address the platform owner typed — never a password a third party chose on the
  merchant's behalf and then knew. The creation form has a "send the link" checkbox and the
  account page has a button for it.
- **`emailVerified` is set true at creation.** Accounts are opened by the platform owner for a
  merchant they have met (Q1); an unverifiable verification wall between them and their first
  sign-in would be ceremony, and the reset link already proves control of the address.
- **The single-template override is written whenever the PLAN allows exactly one template,** not
  when the plan key is `basic`. The admin then picks WHICH one at onboarding and it is stored as
  a per-tenant `templates_allowed` entitlement. Branching on the plan key would violate
  invariant 2 and would silently do nothing the day a second single-template plan exists.
- **Analytics provisioning cannot fail an account creation.** The website is created after the
  tenant exists, failure is logged and reported, and the account page offers a retry. A reporting
  service being down must not stop a merchant being onboarded — and by then the tenant, the
  subscription and the setup-fee payment are already written.

**Handoff to B2:** the merchant-facing `/sign-in`, `/forgot-password` and `/reset-password` pages
live on `app.{DOMAIN}` and belong to B2. Until they exist the emailed set-password link resolves
to a 404 — which is the honest state of a platform whose merchant dashboard has not been built
yet. A1 ships the admin-host equivalents for the platform owner, who otherwise has no way back
into their own panel.

## `admin.{DOMAIN}/` renders sign-in in place

The admin root shows the sign-in card when nobody is signed in, on the same URL, rather than
redirecting to `/sign-in`. Two reasons, and the second is load-bearing: it is the platform
owner's front door, and the shared hostname-resolution e2e asserts that opening the admin root
leaves the URL on `/`. Every other admin route redirects to `/` when unauthenticated.

Sign-in has to exist on this hostname at all *because* cookies are host-only — a session obtained
on `app.{DOMAIN}` is simply not present here. That combination broke once before (trusted
origins never matched `admin.{DOMAIN}`), so `tests/e2e/a1-admin.spec.ts` asserts the cookie
lands on the admin host.

## Both access axes, from the writing side

- Axis (a) writes an `Entitlement`; axis (b) writes a `CapabilityOverride` whose two columns are
  independently nullable, which is what makes the two switches in the panel genuinely
  independent — flipping visibility leaves `editable_by` inheriting the plan.
- **`color_mode` is on axis (a) even though the panel shows it beside the `colors` capability.**
  "Which colours may be chosen" is availability; "who may change them" is edit permission.
  Storing it as a capability would put one product decision in two places that can disagree.
- Every write ends in `invalidateEntitlements(tenantId)`, and a plan edit fans that out to every
  tenant on the plan. The Redis TTL is a net for a missed invalidation, never the mechanism —
  `tests/integration/a1-super-admin.test.ts` asserts the next `can()` call, not a later one.

## The change-request payload contract (A1 defines it, B2 produces it)

`src/server/admin/capability-payloads.ts` is the shape a merchant's "اطلب تعديل" must store, one
zod schema per managed capability. It is written here because A1 merges first and B2 consumes it
from a worktree that does not exist yet. They are JSON shapes, not form shapes: ISO date strings
and numeric coordinates, because the producer is a server action serialising a validated object.

**A payload that does not parse is never applied.** The queue shows the request, says the shape
does not match, and leaves it open. Coercing a merchant's request into something that parses is
how a shop ends up with a map pin in the sea.

Two money rules, both asserted:

- **Rejecting refunds the slot** — by construction, not by bookkeeping. `remainingChangeRequests`
  counts `open` and `applied`, so moving the row to `rejected` IS the refund. A separate counter
  would be a second source of truth and the two would eventually disagree.
- **The ₪25 over-quota add-on is a `change_request_addon` payment LINKED to the request**, recorded
  through `billing.recordPayment`. The link is what lets revenue reporting keep add-ons out of
  recurring revenue; a loose payment with a note could not. Recording it twice is refused.

## Purge calls B1's service and reports honestly when it is not there

`billing.purgeTenant` throws `NotImplementedInPhaseError` until B1 lands. The panel calls it
anyway and renders an Arabic explanation when it throws, rather than deleting the tenant row
itself. Deleting from here would skip the R2 sweep and leave a merchant's whole image library on
object storage with nothing left that knows it exists. The platform audit row is written BEFORE
the call, on the global table, because a tenant-owned row would be destroyed by the cascade it
describes. When B1 merges, the button works with no change in A1.

## Default sections are seeded from the panel

`billing.createAccount` writes a Tenant, a Subscription and a Site — no page structure — and
neither B2 nor B3 exists during Group A. Without something to create the home page and its
sections, a freshly opened account has an empty storefront and "show/hide any section" has
nothing to show. The content tab offers a one-click seed for a site with no sections, built from
`SECTION_TYPES` and the zod schemas' own defaults in `src/shared/site-contract` — never from
`src/templates`, which A2 owns and which is not merged. `gallery` ships disabled so a new shop
does not render an empty grid; `custom_html` is not created at all, since it is feature-flagged
and sanitised at render.

Section reordering is a SWAP of two adjacent `sort` values, not a renumber of the list: a
renumber writes every row on every click, and two admins reordering at once would each overwrite
the other's whole ordering instead of just their own move.

## Forms are server-rendered; exactly one client component holds state

Every mutating form is wrapped in `ActionForm`, the panel's single stateful client component. It
renders one error summary at the TOP of the form in `role="alert"` — which is what a screen-reader
user reaches first after submitting, whereas per-field messages scattered down a long form are
found only by hunting. One-click controls (toggles, section moves, lifecycle actions) are plain
`<form action={serverAction}>` submits that redirect with a message key, so the whole feature
matrix works with JavaScript disabled.

**Validation messages are i18n KEYS, not sentences** (`admin:errors.slugTaken`), resolved by the
form component. Code is English and copy is Arabic (CLAUDE.md), so a server module has no
business holding an Arabic sentence — and a key survives the day a second locale is added. Any
zod issue whose message is not one of our keys becomes `admin:errors.invalidValue`, because a zod
default is an English sentence and an English sentence must never reach a user.

**Dates are read as Asia/Jerusalem wall-clock time.** A browser sends `2026-08-31` from a date
input with no timezone at all; reading it as UTC moves a period end three hours earlier than the
person who typed it meant, which on the last day of a month is a different day.

## Design

`src/app/admin/admin.css` is scoped to `[data-surface="admin"]` so it cannot leak into A2's
templates or B2's dashboard — three surfaces share one document tree. The look is a ledger:
hairline rules instead of drop shadows, tabular figures on every number, one warm accent, and
headings anchored by a short bar on the inline-start edge. That rules out by construction what
CLAUDE.md forbids — no gradient panels, no glass, no shadow soup, no emoji as icons, and nothing
that reads as an untouched component-library default. Switches differ by POSITION and LABEL as
well as colour: a control whose only difference between on and off is a hue is unusable for a
large share of people, and this one grants and revokes access.

## Sync point serviced by the main session

**`tests/unit/language-gate.test.ts` now parses TSX instead of pattern-matching it.** Its JSX
text-node checks were regexes over `>…<`, which cannot tell a JSX text node from ordinary code
between two JSX blocks: `searchParams: Promise<Record<string, string>>` followed by `return (`
and a tag reads as a text node containing the word "return", and so does every `case 'x': return
(` between two rendered fragments. It reported seventeen such "sentences" in A1, none of them
strings. `typescript` is already a devDependency, so an exact `ts.createSourceFile` parse costs
no new package and is strictly stronger: comments are no longer text (the comment-stripping
workaround is gone), and a hardcoded string in a JSX **attribute** — a hole the regex never saw
— is now caught too. Structural attributes (`className`, `href`, …) are exempt from the ENGLISH
scan only; Arabic in any attribute is still a failure.

## Two holes closed at merge review

A1 was built twice — once on `phase-a1`, once here — and the merge review kept this version (it
solves the cross-host impersonation handoff, which the branch left open) after porting the two
concrete defects the branch had found and this one still had:

- **The offered-plan restriction is re-checked server-side.** The creation form's `<select>` is
  filtered to `!hidden && active`, but `planKey` arrives as free-form text in the POST body, and
  nothing downstream stopped it: `assertPeriodEndAllowed` only rejects a NULL period end on a
  *visible* plan, and `billing.createAccount` sets `isDemo: plan.hidden`. Posting `demo` therefore
  created a **paying** merchant behind proxy.ts's demo-token gate, force-noindexed, with the ₪350
  skipped and the tenant eligible for B3's close-demo, which deletes it outright. This is
  invariant 2 exactly — never let a route trust the client about availability — and a filtered
  dropdown is not a server-side check.
- **A failed `billing.createAccount` no longer strands the owner's email.** The owner `User` is
  written before billing (billing needs a user id to attach the membership to) and outside its
  transaction, so any failure left a user holding the merchant's address; the `emailTaken`
  pre-check then refused the operator's own retry permanently, on a row that appears on no screen
  in the panel because a user with no membership is on no account page. `discardOrphanOwner`
  deletes only a user that belongs to **no** tenant — if the failure landed after billing's insert
  committed, that user is a real owner and removing them would leave a live account unowned.

Both are pinned by `tests/integration/a1-super-admin.test.ts`, and both were confirmed to fail
against this file before the fix rather than merely pass after it.

## Known gaps at the end of A1

- **The impersonation banner is B2's** (see above). A1 ships both endpoints and the copy.
- **The merchant password-set link resolves to a 404 until B2 ships `/reset-password` on `app.*`.**
- **Analytics visit counts are unverified against a live service.** The client degrades on every
  failure path and the account page names which one it hit; nothing in CI exercises a real
  analytics container.
- **Payment attachments are a picker over existing media, not an upload.** Uploading is A3's
  pipeline, which does not exist yet; an upload button that cannot upload is worse than an honest
  empty state.
- **No demo screens exist here** — `src/app/admin/demos/**` belongs to B3, and a unit test asserts
  A1 built nothing under that path.
