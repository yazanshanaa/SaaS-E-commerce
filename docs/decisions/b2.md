# B2 — Merchant dashboard

Decisions taken while building `app.{DOMAIN}`. Folded into `docs/DECISIONS.md` at the merge.

---

## The sync point B2 could not build without

**A merchant's session did not know which shop it was in.** better-auth sets
`activeOrganizationId` only from `POST /organization/set-active`, and nothing on this platform
called it — so `getSession()` resolved BOTH `tenantId` and `memberRole` as null for every
merchant, and every consumer refused the person it belonged to: this whole surface,
`requireMerchant()`, and A3's `/api/media/upload`, which reads `session.tenantId` directly.
Impersonation had the same hole from the other side, since `impersonateUser` mints a fresh
session that inherits nothing from the admin's — A1's Q17 sales tour would have landed on a
dashboard that could not name the tenant it was showing.

`src/server/auth/**` is forbidden to a track, so this went to the main session and is recorded in
`docs/DECISIONS.md` with the two halves it needed (a session-create hook writing the MODEL field
name, and `getSession()` reading it under the same name). B2 rebased onto the fix. The reason it
survived Phase 1 is worth keeping: the existing membership suite asserted the RLS policy and the
`authDb(userId)` call, both of which were correct — the bug lived in the gap between a hand-built
session object and a real one, so the new test drives the real sign-in API.

## Routing and ownership

- **`/reset-password` and `/forgot-password` are B2's**, and `/reset-password` is not optional
  decoration: it is the `redirectTo` that A1's owner invitation and this track's staff invitation
  both pass to better-auth. Without it every account ever created on this platform receives a
  working link to a 404. A1 says the same thing from the other side in
  `_components/password-forms.tsx`.
- **The self-serve export screen is `/settings/export`, never `/export`.** `/export/{token}` is on
  proxy.ts's UNPREFIXED list because it is a link handed to a suspended merchant over WhatsApp
  (Q18); taking `/export` for a dashboard screen would collide with a promise already made to
  someone outside the platform.
- **The nav is built on the server from both access axes.** Rendering the full list and hiding
  items in the browser would ship a staff member an inventory of the screens that are not theirs,
  and would eventually disagree with the routes, which check for themselves.
- **A refused scope is a 404, not a 403** — for a wrong role and for a missing feature alike.
  Telling a staff member that a billing screen exists and is not theirs is a map of what to try
  next; telling a basic-plan merchant that an analytics screen exists behind a plan is a sales
  pitch the page was not asked to make.

## Scope calls

- **Category CRUD lives here.** `docs/PHASES.md` lists "category" as a product FIELD and never
  says who creates one — and nobody else can: A1's site-content tab does not manage them and B3
  only seeds demo packs. Without it a merchant could pick a category and never make one, and A2's
  categories section would render empty forever on every real account. A category is part of the
  catalogue, not appearance, so it follows products rather than the capability axis.
- **A category KEY is generated once and never rewritten from a rename.** It is the storefront's
  stable handle and what B3's packs link products by.
- **Custom domains are a REQUEST here, not a provisioning flow.** Phase 4 owns verification, the
  `domains_limit` enforcement, the CNAME runbook and the Caddy on-demand TLS ask. Writing a
  `pending` Domain row now would put a hostname into a globally unique column that nothing can
  verify or clean up — and `domains` is the table `proxy.ts` resolves strangers against. The
  screen shows existing rows read-only and records an audited request.
- **No orders inbox and no placeholder for one** (Q5). The `staff` role's `orders` scope simply
  has no surface until Phase 5.
- **The logo is carried through as a hidden field rather than edited.** It is a media id, and a
  text box asking a shop owner for a database identifier is worse than no control; a picker
  belongs with the media work. Carrying it preserves whatever A1 or B3 set instead of blanking it
  on every save. Same reasoning for `imageMediaId` / `mediaIds` in the section settings form.

## Access axis (b), as a merchant experiences it

- **`editable_by = admin` renders the field, filled in and read-only, with the change request
  attached to the same submit.** So the merchant picks the colours they want and asks for them in
  one gesture, rather than describing a colour in a text box. The payload builders live beside the
  writers in `_lib/site.ts` for exactly this reason: the two must describe the same change.
- **Every locked write is refused on the SERVER by `canEdit`, not by the form.** A tab left open
  when the platform owner flips `editable_by` must not still be able to save.
- **The board request carries the WHOLE board, not one card.** `announcementsBoardPayload` is an
  array A1 applies verbatim, and an array of one would read as "these are the announcements".
- **`sectionsLayoutPayload` carries `{id, enabled, sort}` and nothing else**, so a locked merchant
  can ask for a reorder precisely and describes any config wish in the note field. That is a real
  limit of the frozen contract rather than an oversight, and the note is what keeps the request
  usable instead of silently dropping half of it.
- **A merchant who MAY edit a capability cannot spend a quota slot on it**, and staff can never
  spend one at all. Both are refusals in the service, because the screen that would prevent them
  is not the boundary.

## Things that were nearly wrong

- **Float prices.** `Math.round(Number(value) * 100)` makes `19.955` into ₪19.95, because
  `19.955 * 100` is `1995.4999999999998`. The parser now splits the string at the decimal point
  and decides the rounding on the third DIGIT. One agora on one product is nothing; a pricing rule
  that disagrees with arithmetic is not, because every price on the storefront goes through it.
- **`issue.message.includes(':')` as a test for "is this one of our i18n keys".** Zod 4's own
  messages are sentences like `Too small: expected string to have >=3 characters` — which contain
  a colon and sailed straight through. They never reached a merchant (the resolver refuses an
  unknown namespace), but every ordinary zod failure became indistinguishable from a message we
  wrote on purpose. The check is now the key SHAPE. **A1's `fieldErrorsFromZod` has the same
  substring check**; it is A1's file, so it is raised here rather than edited.
- **Over-admission on the product limit.** Count-then-insert lets two saves both read `used = 29`
  on a 30-product plan. The tenant row is locked `FOR UPDATE` first, mirroring what A3 does for
  storage.
- **An absent `products_limit` is zero, never unlimited.** A missing feature means we could not
  establish what the tenant is entitled to, and writing on that basis is how a plan gets bypassed.

## Borrowed rather than duplicated

- **`isCustomHtmlAllowed` comes from A2** (`src/templates/lib/custom-html-gate`). There is no
  `custom_html` feature key, so A2 pinned the substitute (`seo_tools`) and the demo exclusion in
  one constant. A second copy here is exactly the drift that ends with a dashboard saving a block
  the storefront refuses to render.
- **`CAPABILITY_PAYLOAD_SCHEMAS` comes from A1**, which is where the contract was written down
  because A1 merged first. B2 writes those payloads; A1 applies them verbatim.
- **Media errors carry their sentence, not their key.** `MediaError.arabicMessage` is already
  `t('media', 'errors.<code>', params)` with limits A3 owns and this surface does not hold, so
  `FieldError` gained an optional `message` for that one case. `messageKey` stays required, so a
  caller must still name the message it means.
- **The impersonation banner reads its copy from the `admin` namespace.** B2 owns the banner, A1
  owns the copy and the stop endpoint — a split forced by the session being minted on one host and
  landing on another. Duplicating the copy would let the two drift.

## Known limits, carried forward

- **`pnpm build` and `pnpm e2e` cannot run from a Group B worktree.** Its `node_modules` is a
  symlink into the main checkout and Turbopack refuses it (*Symlink [project]/node_modules is
  invalid*). Not a code problem and not new to this track — the worktree bootstrap used a link
  instead of `pnpm install`. Both gates were run in the main checkout at the merge.
- **`staffInviteTemplate` is still unused.** The invitation reuses better-auth's password-reset
  flow, exactly as A1 does for a new owner, because the reset URL only exists inside the
  `sendResetPassword` hook in the forbidden auth config. The screen's Arabic promises what
  actually happens ("بنبعتله رسالة على بريده عشان يعيّن كلمة مروره"), so the merchant is not
  misled — but the nicer invite copy needs an auth-layer change to be reachable.
- **A removed staff member's identity is deleted when it belongs to no other tenant**, through the
  same member-count check A1 uses for an orphan owner. It inherits the known race recorded at the
  B1 merge: two concurrent removals of a user shared by two tenants can leave the row behind.
  Phase 6.
