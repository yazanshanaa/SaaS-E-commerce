# B1 — Subscription lifecycle and notifications

Decisions taken while implementing B1. Folded into `docs/DECISIONS.md` by the main session at merge.

---

## 0. MERGE BLOCKER — the ownership checker cannot pass for B1 as written

`npx tsx scripts/check-track-ownership.ts b1 ../sb-b1` reports **16 violations**, all of them
files B1 is explicitly supposed to own. This is a bug in the script, not in the branch.

The script's own comment says the exception is expressed as ownership rather than as a hole:

```ts
/**
 * Touched by no worktree, ever. The two documented exceptions (B1 fills in `billing` and the
 * images half of `export` during Group B) are expressed as ownership entries for B1 rather than
 * holes here, so the default stays "forbidden" for everyone else.
 */
const FORBIDDEN = [ … 'src/server/billing/**', 'src/server/export/**', 'src/server/jobs/**', … ];
```

…and `OWNERSHIP.b1` duly lists all three. But `main()` never gives ownership a chance:

```ts
if (matches(reserved, file))       violations.push(…)
else if (matches(forbidden, file)) violations.push(…)   // <- always wins
else if (!matches(owned, file))    violations.push(…)
```

**The fix, for the main session** (`scripts/**` is forbidden to a track, so this is a sync point):

```ts
if (matches(reserved, file))       violations.push([file, 'reserved for another track inside your own folder'])
else if (matches(owned, file))     continue                     // ownership beats FORBIDDEN
else if (matches(forbidden, file)) violations.push([file, 'FORBIDDEN shared file — this is a sync point, not an edit'])
else                               violations.push([file, `outside ${track}'s ownership`])
```

Safe for every other track: `RESERVED_WITHIN` is still checked first (so B3 still cannot touch
`src/server/demo/types.ts`, and B1 still cannot touch `src/server/billing/demo-content.ts`), and
no other track lists a forbidden path in its ownership. `src/server/queues.ts`,
`src/server/storage/**` and `src/server/revalidation/**` remain forbidden to everyone because
nobody owns them.

Verified by re-running the same rules with the documented precedence: **all 25 changed paths are
inside B1's ownership, clean.** The 25 are `src/server/billing/**` (4), `src/server/export/**` (5),
`src/server/jobs/**` (7), `src/app/admin/lifecycle/**` (5), `messages/ar/billing.json`, and three
`b1-*` test files — plus this document.

## 1. A job whose body is a billing TRANSITION is system-scoped

`suspend-tenant` and `purge-tenant` are dispatched as **SystemJobs carrying `tenantId` in the
payload**; `send-reminder` stays a TenantJob. The rule that produced that split:

> A job that performs ONE tenant-scoped unit of work is a TenantJob and uses the transaction the
> worker already opened. A job whose body is a billing transition is a SystemJob, because the
> transition opens and closes its own tenant transactions — and must.

Three forcing reasons, none of them stylistic:

1. **Suspension's two effects are two commits (Q18).** `createWorker` wraps every TenantJob in
   `withTenantTxn` for its whole duration. Running `billing.suspend()` inside that erases the
   boundary the design exists to create, and re-creates the exact failure it prevents: an export
   error rolling the suspension back, leaving a non-paying storefront open with `retentionUntil`
   unset.
2. **The export zips gigabytes.** A TenantJob wrapper guarantees a Postgres transaction is held
   for the whole build — pinning a connection for minutes and hitting the interactive-transaction
   timeout on precisely the pro tenants who most need the artifact.
3. **The purge's own guard would make it un-retryable.** Step 0 marks the tenant `purging`, and
   `withTenantTxn` refuses a purging tenant. As a TenantJob, the first attempt would succeed and
   every retry after a mid-purge crash would throw `TenantPurgingError` — stranding the tenant
   half-purged, serving nothing, deletable by nothing.

Invariant 8 still holds where it matters: these processors run as `app_system`, which has no write
grant on any tenant-owned table, and every write they cause happens inside a `withTenantTxn` that
sets the RLS context. What moved is only *who opens the transaction*.

## 2. The verify phase, because BullMQ's retry state is invisible from inside a processor

The gate asks for an alert when the export "fails all retries". A processor is handed a parsed
payload, not the BullMQ job, so it cannot know it is on the last attempt. Two mechanisms replace
that, and both catch a failure mode a retry counter would not — a job that was dropped, or a
worker that died before running it:

- `suspend-tenant` is enqueued **twice** by `billing.suspend()`: once as `phase: 'export'`, once
  as `phase: 'verify'` with a 30-minute delay. The verify phase re-reads `exportKey`; still null
  means every attempt failed, so it raises a `super_admin` Notification and emits
  `subscription.export_failed`.
- The nightly sweep is the backstop: any suspended subscription with no `exportKey` more than two
  hours after `suspendedAt` gets its build re-enqueued and its verification re-scheduled.

Both are idempotent — `notifySuperAdmin` writes at most one unread alert per key per tenant, since
an alert channel that repeats every morning is one people learn to ignore.

A second registered job name would have read better and was not available: `src/server/queues.ts`
is a forbidden shared file, so a track can only fill in a name Phase 1 declared. The phase rides in
`data` instead, and `tests/unit/b1-lifecycle-contract.test.ts` asserts every name B1 enqueues is
actually registered — a typo there would enqueue happily and never run.

## 3. Enqueue and drain are bounded and best-effort

`queueRedis()` is configured with `maxRetriesPerRequest: null` because BullMQ blocks on
BRPOPLPUSH. The consequence on the **web** side is that a command against a dead Redis never
settles — so an admin pressing "suspend" or "delete now" would get a spinner that never ends.

`src/server/billing/dispatch.ts` therefore races every broker call against a 5-second timer and
swallows the failure with a log line. That is correct beyond the timeout: a suspension COMMITS
first and schedules its export second, so an enqueue failure must not be reported to the caller as
a failed state change — and the sweep re-enqueues anything that went missing. The same wrapper
covers `drainTenantJobs`, so a purge still runs with the broker down; `withTenantTxn` refusing a
purging tenant is the second layer for whatever was already dequeued.

The seams (`setJobDispatcher` / `setJobDrainer`) are what let the whole lifecycle be tested against
a real PostgreSQL with **no Redis at all**.

## 4. `createMany`, not `create`, on the two global audit tables

`tenantTombstone.create()` and `platformAuditLog.create()` both failed with
`new row violates row-level security policy`, and the reason is not the INSERT policy — it is the
`RETURNING` clause. Prisma's `create()` compiles to `INSERT … RETURNING`, and Postgres applies the
**SELECT** policies to the returned row. Both tables are readable by a super admin only, and both
writes happen as the `system` actor, so an insert the policy explicitly permits is refused on the
read-back.

`createMany` returns a count and touches no SELECT policy. On the tombstone it also brings
`skipDuplicates`, which is what makes a purge resumable after a crash between the tombstone and the
cascade — the alternative, checking first, is unavailable for exactly the same reason.

## 5. A purge deletes the merchant's identity too

`users` is a global table, so the cascade never reaches it — a purged merchant would otherwise keep
their name and email on the platform forever, which contradicts the deletion the tombstone exists to
prove. `purgeTenant` (and `closeDemo`) therefore delete every member user whose **only** membership
was this tenant; a person who is staff at two shops keeps their account.

Two constraints shape how:

- The cross-tenant "do they belong anywhere else?" question cannot be answered from a tenant
  context (`members` is under generic isolation), so it runs as `app_system`, which has SELECT and
  no write grant.
- The delete must happen **before** the tenant, because the `user_access` policy admits a user
  through `EXISTS (member row in the current tenant)` — and that row disappears with the tenant.

## 6. Storage is resolved BEFORE the purge writes anything

Found by the e2e stack, which runs `next start` with `NODE_ENV=production` and no object storage:
`storage()` refuses to serve media off the app server's disk in production (invariant 4), and the
purge discovered that at step 1 — *after* step 0 had committed `purging`. The tenant was left dark,
un-writable, and waiting for a sweep that would keep failing identically.

`purgeTenant` and `closeDemo` now resolve the adapter as their first statement. It is not a health
check — a transient network failure still surfaces at step 1, where a retry resumes correctly. It
closes the class of failure that never resolves itself. The lifecycle screen's purge action also
catches an unexpected failure and reports Arabic copy instead of Next's error page.

## 7. The export is a real ZIP, with a bounded image budget that says so

Phase 1 shipped the CSVs concatenated into one text blob under a `.zip` key. B1 replaces it with an
actual archive (`archiver` — ESM, named exports only in v8, so `new ZipArchive(...)` rather than a
default factory) containing `README.txt`, `products.csv`, `categories.csv`, `images.csv` and one
image per product photograph.

- **One variant per image, `full` first, WebP before AVIF.** Shipping all six variants would
  multiply the artifact by six for no gain. WebP wins over the smaller AVIF because this file is
  opened *off* our platform — on an old phone, a desktop viewer, a competitor's importer.
- **`MAX_EXPORT_IMAGE_BYTES = 192 MB`, and the README says when it bit.** `StorageAdapter.put()`
  takes a Buffer, so the archive is materialised in memory; a pro tenant at the 10 GB storage limit
  would take the worker down. A truncated export that *states* it is truncated will not. A silent
  cap would read as "we gave you everything".
- **Three phases: read (short txn) → build (NO txn) → stamp (short txn).** Phase 1 did all three
  inside one 120-second transaction, which was fine for a text blob and would not be for a
  gigabyte of photographs. `exportTenantData` also accepts the caller's `tx`, so `build-export`
  stops opening a second transaction on a second connection for reads its own could answer.
- **The archive is byte-stable for identical input** (fixed entry dates), so the deterministic
  suspension key is a genuine overwrite rather than two different files under one name.

## 8. Arabic copy is Arabic copy, including inside the ZIP

The README a merchant opens is user-facing, so every sentence comes from `messages/ar/billing.json`
and file names are interpolated as `{parameters}` — otherwise the language gate would (correctly)
flag `products.csv` as stray Latin in the catalogue.

In-platform notices are `Notification` rows carrying an i18n **key** plus a data bag, never a
rendered sentence: storing Arabic in the database would put copy where it cannot be corrected,
cannot be re-rendered when a merchant renames their shop, and is the one user-facing string the
language gate cannot see. The WhatsApp message itself is not sent from here — it goes out as an
Event through the HMAC-signed dispatcher to n8n; the row is the platform's own copy of the fact.

## 9. `DEMO_PACKS` lives in `src/server/billing/demo-packs.ts` — B3 should consume it

`createDemo` writes the `Site` from the pack's identity block before handing the transaction to
B3's content builder, so the lifecycle half has to read a pack, and B1 lands first. The registry is
exported from `src/server/billing`. **B3 should import `DEMO_PACKS` / `demoPack()` rather than
writing a second loader** — two independent readers of the same frozen JSON is how a pack picker
ends up offering a pack that creation cannot resolve. The data stays frozen either way.

`createDemo` creates the tenant skeleton (tenant, subscription, site, login-disabled owner) through
the super-admin client, then opens ONE `withTenantTxn` for the content, the `DemoLink` token and the
`demo.created` event. Atomicity holds where it matters: the token is what makes a demo shareable, so
a failure anywhere in the build leaves no link at all, and the skeleton is unwound in the catch.
That path is tested today against B3's still-throwing stub.

## 10. Review fixes — what a green gate could not see

Found at merge review by an eight-dimension adversarial pass over the branch (32 raw findings, 15
surviving verification). Every one of these passed typecheck, lint, 617 unit and integration tests
and 75 e2e specs before it was found, which is the point of writing them down.

### The export could stamp a subscription it no longer belonged to

Phase 2 of the export holds NO transaction — deliberately, because zipping a pro catalogue is
minutes of I/O — so the row can move underneath it. The stamp was an unconditional
`update({ where: { tenantId } })`, so whatever finished last won:

- **Reactivated mid-build.** The merchant pays, `reactivate` nulls the columns and calls
  `delete(exportKey)` on a key that is still null, so it deletes nothing. The build then lands and
  stamps `exportKey` onto a now-ACTIVE row. That is a live paying account carrying a standing
  snapshot of its own catalogue — the exact thing PHASES.md says reactivation exists to remove —
  and nothing would ever collect it, because `_exports/` is excluded from orphan cleanup by
  design. The job then emitted `subscription.suspended`, so the merchant who had just paid got a
  WhatsApp saying their site was closed, carrying a link built from the revoked token.
- **The next suspension inherits it.** `runSuspensionExport` skips the build when `exportKey` is
  set, so that stale key would later hand the merchant a WORKING link to the previous period's
  catalogue. Wrong data delivered is worse than a missing artifact: nothing looks broken.

Three changes: the stamp is now `stampSuspensionExport()` in `src/server/billing` — conditional on
`status: 'suspended'` AND the same `suspendedAt`, returning whether it landed; `exportTenantData`
takes the object back when it did not; and `runSuspensionExport` re-reads the row inside the
transaction that emits, so the message is built from the CURRENT token and is skipped entirely if
the suspension is no longer the one it built for.

The stamp lives in `billing` and not in `export` because its WHERE clause is lifecycle state.
`tests/unit/guardrails.test.ts` (invariant 5) caught the first attempt to put it in `export` — the
guardrail was right, and the design is better for it.

### "Re-send export link" revoked the link and sent nothing

`reissueExportLink` rotated the token — killing the link already in the merchant's phone — emitted
no event, and returned a URL the server action discarded. The screen deliberately never prints a
link, so the operator could not read it out either, while the success copy told them to send it.
A merchant who called because they lost their WhatsApp ended up with no working link at all,
and pressing the button again only rotated it a third time.

It now re-emits `subscription.suspended` with the fresh link, plus the merchant Notification —
and sends NOTHING when no artifact exists, because a second promise of a copy that was never built
is the failure this whole path is built around. It re-uses that event rather than a new type on
purpose: `WebhookEndpoint.eventTypes` filters delivery, so a brand-new type would reach nobody
until every endpoint is reconfigured — silently not sending, all over again.

### The sweep could schedule an export for a tenant it was purging in the same pass

`missingExports` had no upper bound against `retentionUntil`, so one pass fanned out both a purge
and an export rebuild for the same tenant, and the lifecycle queue runs five jobs at a time. The
purging guard stops a job that STARTS late; it cannot stop one already zipping. Its `put()` could
therefore land after the prefix sweep — a full copy of the catalogue written into a prefix whose
Tenant row is then deleted, which is the "quiet retention" failure the design exists to prevent,
arriving by accident instead of by policy. Bounded with `retentionUntil: { gt: now }`: an artifact
built minutes before deletion is a link nobody will ever open.

The same query family was missing `currentPeriodEnd: { not: null }` on all three suspended-side
queries, while the file's own docstring claimed every query excluded demos. A demo suspended by
any route would have been warned about a deletion date and then purged WITH a tombstone — exactly
what `closeDemo` exists to avoid. The docstring is now true.

### The recovery button was silently dropped by the broker

`rebuildExportAction` reused `suspend-export:{id}:{stamp}` — the id the suspension itself
enqueued. BullMQ treats `add` with an existing job id as a no-op, and the failed job is still in
the queue, which is exactly the state an operator presses this button in. So the recovery action
for a failed export reported success and did nothing; only the nightly sweep ever rebuilt
anything. It now uses a distinct id at minute granularity — a double-click is still one job.

### Smaller, and all of them user-facing

- `subscription.export_failed` was emitted on every verify run while the alert beside it was
  idempotent, so a permanently failed export fired a fresh webhook every night for the rest of the
  window. It now follows `created`.
- `notifications.suspended` and `notifications.purgeScheduled` interpolated a `{link}` that no
  caller ever supplied, so B2's dashboard would have rendered a literal `{link}` to a merchant.
  The copy now says where the link was sent instead of pretending to carry it — storing the URL in
  the row would have been worse, since rotation would leave a dead link behind.
- `subscription.reactivated`, `subscription.retention_extended` and `demo.converted` went to the
  outbox with `tenantName: ''`. The first two are inherited from Phase 1 rather than introduced
  here; all three now carry the name, because a merchant with two shops cannot tell from the
  message which one it is about.

### Three tests that proved less than they claimed

- **"still downloads on day 29"** advanced `vi.setSystemTime`, but the window is enforced by the
  `subscription_export_token_lookup` policy — `retention_until > now()`, Postgres's clock, which a
  faked JS clock does not move. It passed identically at day 4000, which is the one result that
  would mean the window was broken. It now ages the ROW, and asserts the same token is REFUSED
  once the window closes — the half that proves the first half measured anything.
- **"purging while a media job is queued leaves zero objects"** queued no job and stubbed the
  drainer to return a number. Nothing was ever going to write an object, so the assertion held
  vacuously. It now enqueues a real job, drains it the way `removeTenantJobs` actually decides
  (on the payload's `tenantId`), and separately proves that a job which survived the drain is
  refused by the purging guard.
- **the export-failure test** asserted the notification count and called it "no second alert",
  while the outbound event was firing every run. It asserts both now.

## 11. The operator's door into the purge/export race, and why it needed two layers

An independent audit against the two failures in `docs/PHASES.md` found the one path section 10
did not close. The sweep learned `retentionUntil > now`, so a single pass can never fan out a
purge and an export rebuild for the same tenant. **The operator paths never learned anything**:
`/lifecycle/pending-purge` lists a tenant suspended thirty seconds ago — whose export is still
zipping — immediately next to «حذف الآن», and `purgeAccount` calls straight through with no
precondition beyond `assertTransition`. Phase 2 of the export holds no transaction by design, so
its `put()` lands after `deleteByPrefix` has already run. That is failure 1 verbatim: a complete
copy of the merchant's catalogue on R2, under a prefix whose Tenant row is then deleted, inside
the one prefix `cleanup-orphans` skips by design.

**Layer one — refuse.** `purgeTenant` throws `ExportInFlightError` when the subscription has no
`exportKey` and was suspended less than `EXPORT_IN_FLIGHT_WINDOW_MS` (2h) ago. Scoped to
`reason === 'super_admin_purge'`, and the scope is load-bearing rather than tidy: the sweep's
`retention_expired` purge is already bounded on both sides, and it takes an *injected* `now` while
this guard reads `Date.now()` — an unscoped version fails the sweep's own tests, for a reason that
would be just as real in any environment where the two clocks disagree. Exempt for an
already-`purging` tenant, because this transaction opens with `allowPurging` so a crashed purge
can resume, and a guard that refused the retry would strand it half-deleted (§1).

**Layer two — compensate.** The window is time-bounded on purpose, so a purge *can* still land
mid-build once an export has been failing for hours. Section 10's conditional stamp already took
the object back when the stamp was refused — but only when it *returned false*. `withTenantTxn`
throws `TenantNotFoundError` / `TenantPurgingError` **before** `fn` runs, so the purge case
propagated out of `exportTenantData` and skipped the compensation entirely. Those two errors now
land as `stamped = false`, which is what the existing compensation was always for.

Only those two. Any other failure leaves the object alone: a connection lost after COMMIT is
indistinguishable from a rollback here, and deleting an object a committed stamp points at would
hand the merchant a link to nothing. The key is deterministic, so a retry overwrites.

Both layers have tests that fail without them — verified by reverting `src/` and re-running.

## Open items for the main session

1. ~~**The ownership checker precedence bug** — section 0.~~ **Fixed in the main session at merge**:
   ownership is now evaluated before FORBIDDEN, with `RESERVED_WITHIN` still first. B1 reports
   clean; a1/a2/a3/b2/b3 are unaffected, because no other track lists a forbidden path.
2. **`removeTenantJobs` matched only TenantJobs** — `src/server/queues.ts`, forbidden to a track,
   **fixed in the main session at merge**. Phase 1 filtered on `scope === 'tenant'`, which was
   complete when every job that named a tenant was a TenantJob. Section 1 above made
   `suspend-tenant` and `purge-tenant` SystemJobs carrying `tenantId` in the payload — so the
   purge's quiesce step silently stopped draining the two jobs most worth draining. It now matches
   on the payload's `tenantId`.
3. **No navigation entry points at `/lifecycle`.** `src/app/admin/_components/nav.tsx` and
   `messages/ar/admin.json` belong to A1, so B1 cannot add the rail link that makes its own screens
   reachable. One line each:
   ```ts
   // src/app/admin/_components/nav.tsx
   { href: '/lifecycle', key: 'lifecycle' },
   ```
   ```json
   // messages/ar/admin.json → nav
   "lifecycle": "دورة الاشتراكات"
   ```
   Until then the screens exist and answer, but only by typing the URL.
4. **The worktree's `node_modules` was a symlink** into the main checkout, which Turbopack rejects
   ("Symlink [project]/node_modules is invalid, it points out of the filesystem root") — so
   `pnpm build` could not run in `sb-b1` at all. Replaced with a real `pnpm install --frozen-lockfile`
   plus `prisma generate`; `pnpm-lock.yaml` and `package.json` are unchanged. Worth fixing in the
   bootstrap instructions before the next parallel group.
5. **Phase 7 already owns the real-storage gap** ("Export machinery end-to-end against REAL
   storage"). The e2e stack cannot exercise a successful purge, because it runs in production mode
   with no object storage — see section 6. The successful path is covered by the integration suite
   against real files on disk.
6. **`EXPORT_VERIFY_DELAY_MS` (30 min) and `MAX_EXPORT_IMAGE_BYTES` (192 MB) are module constants,
   not env vars**, because `.env.example` and `src/env.ts` are forbidden to a track. If either
   should be tunable per environment, that is a one-line sync point.
7. **Two purges running concurrently can orphan a shared identity.** `usersWithNoOtherMembership`
   asks "does this person belong anywhere else?" before each tenant is deleted. If A and B are
   purged at the same moment and one person is a member of both, each purge sees the other
   membership and neither deletes the User — leaving a name and an email address on the platform
   after both shops are gone. NOT fixed here, because the honest fix is a global sweep for
   member-less users and RLS puts that out of reach: `app_system` may read `members` and has no
   write grant, while `app_web` can only delete a User through a member row in the current tenant,
   which is exactly what has just disappeared. Carried to Phase 6 with the data-subject work.
8. **`demo.closed` carries the demo's plaintext slug into `webhook_deliveries`, which is global
   and outlives the tenant.** `closeDemo` deliberately writes no tombstone so that nothing derived
   from the prospect's own requested prefix survives — and then emits an event whose delivery row
   keeps that prefix in the clear. NOT changed here: the payload shape is frozen in
   `src/server/events/types.ts`, whose stated rule permits identifiers (it forbids credentials),
   and `demo.created` has the same property from Phase 1, so a fix is a vocabulary change plus a
   deliveries-retention decision. Belongs with the Phase 6 privacy pass, not with a merge.
