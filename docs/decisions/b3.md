# B3 — Demo generator and the demo surface

What was decided while building `src/server/demo`, `src/app/admin/demos/**` and
`src/app/(public)/**`, and why. Sync points first: those are the things the main session has to act
on, and two of them fail the build until it does.

---

## Sync points — the main session must land these

### 1. `tests/unit/a1-admin-contracts.test.ts:205-211` fails, by design

```ts
it('builds no admin screen for demos — that whole surface belongs to B3', () => {
  const adminRoutes = walk(path.join(repoRoot, 'src', 'app', 'admin')).map(…);
  expect(adminRoutes.filter((route) => /\/demos?\//.test(route))).toEqual([]);
});
```

A1 wrote it to hold the demo surface open until this track arrived, and it does exactly that: it
goes red on B3's first page. The file is A1's (`tests/**/a1-*.test.ts`), so B3 cannot legally fix
its own blocker.

**Replace it with the assertion it was standing in for** — that the demo screens do not reach around
billing:

```ts
it('drives every demo lifecycle change through billing, never directly', () => {
  const demoSources = walk(path.join(repoRoot, 'src', 'app', 'admin', 'demos')).map(read);
  const offenders = demoSources
    .filter(({ source }) => /\.tenant\.(create|delete)\s*\(|\.subscription\.(update|create)\s*\(/.test(source))
    .map(({ rel }) => rel);
  expect(offenders).toEqual([]);
});
```

### 2. `tests/integration/b1-lifecycle.test.ts:872-895` fails, by design

```ts
await expect(createDemo({ … })).rejects.toThrow(/B3/);
```

Its own comment says why: "B3 has not landed, so `buildDemoContent` still throws — which makes this
the one moment the unwind path can be tested against a genuinely failing builder." B3 landing is the
end of that moment. The file is B1's.

It currently fails with `media error: limitsUnavailable` rather than `/B3/`, which is a second,
quieter problem in the same test: that file's `beforeAll` seeds `ensurePlan('demo', { hidden: true })`
with **no features**, so `resolveStorageLimits` finds no `image_max_mb` / `storage_mb` and the build
fails closed before it writes anything. Any future B1 test that creates a demo needs the features.

**Replace it with a failure the product can actually have** — object storage refusing a write, which
is what `tests/integration/b3-demo.test.ts` ("leaves nothing behind when the build fails half way")
does. The coverage is not lost in the meantime: that test asserts the same three properties (no
tenant, no owner user, no stranded objects).

### 3. The rail has no way into `/demos`

`src/app/admin/_components/nav.tsx` is A1's and outside the `src/app/admin/demos/**` carve-out —
the same wall B1 hit, and its comment records the resolution: "wired in at the merge". Add, after
`/lifecycle`:

```ts
{ href: '/demos', key: 'demos' },
```

and `nav.demos` to `messages/ar/admin.json` (`"النسخ التجريبية"`). Until then the screens are
reachable only by URL.

### 4. A demo owner cannot be impersonated — half an acceptance criterion cannot pass

The gate reads: *"the demo's owner user cannot authenticate by any route, **while impersonation from
A1 reaches the dashboard normally and shows the staff-accounts feature**"*. The first half holds and
is tested. The second cannot, today:

```ts
// src/server/auth/config.ts:196-214 — databaseHooks.session.create.before
const user = await authDb().user.findUnique({ where: { id: session.userId },
                                              select: { loginDisabled: true } });
if (user?.loginDisabled) {
  logger().warn({ userId: session.userId }, 'refused session for a login-disabled user');
  throw new Error(t('common', 'auth.accountDisabled'));
}
```

A1's `startImpersonation` calls `auth().api.impersonateUser(...)`, which MINTS A SESSION for the
demo's owner — and this hook refuses it. The hook's own comment says the opposite is intended
("exists so the tenant is ownable and **impersonable for the sales tour (Q17)**"), so the guard is
one condition short rather than wrong:

```ts
// An impersonated session is minted BY a verified super admin, for a user that has no credential
// account to sign in with. Refusing it closes the sales tour Q17 exists for.
if (user?.loginDisabled && !session.impersonatedBy) { … }
```

`src/server/auth/**` is forbidden to every track. Until it lands, `createDemo` produces exactly the
owner the spec describes and nothing can use it.

### 5. A public demo request notifies nobody out of band

`docs/PHASES.md` says the form "creates a `DemoRequest` row and notifies the admin". The platform's
notification table cannot carry that message: `Notification.tenantId` is NOT NULL with a foreign key
to `tenants` (`prisma/schema.prisma:1316-1331`), and a demo request exists precisely because no
tenant does yet — `notifySuperAdmin(tx, { tenantId, … })` has nowhere to hang it.

What B3 shipped instead is a pending count on the inbox tab, which reaches an operator who is already
in the panel and nobody else. The real fix is a nullable `tenantId` (or a platform-scoped
notification), which is a migration and therefore main-session work. Phase 4's push work will want
the same thing.

### 6. The e2e stack cannot write media, so half this suite is skipped

`playwright.config.ts` runs the built app with `NODE_ENV=production` **and** `STORAGE_DRIVER=local`,
and its own comment explains why that was safe: *"The dev media route refuses to run in production;
nothing in this suite serves media."* That stopped being true with B3, whose central act writes
fifteen images. `storage()` refuses the pair by invariant 4 —

```
STORAGE_DRIVER=local is not allowed in production: media must be delivered by the CDN in front of
R2, never from the app server disk.          (src/server/storage/index.ts:40)
```

— so every demo CREATION in the e2e stack fails with the Arabic «صار خلل», and with it the approve →
link → storefront → close chain. Confirmed by running it: the four request-side tests pass, and the
three that need a built demo are `test.describe.skip`ped with the reason inline. The same behaviour is
covered meanwhile by `tests/integration/b3-demo.test.ts` against a real database and a real disk.

B3 cannot fix it — `playwright.config.ts`, `src/env.ts` and `src/server/storage/**` are all forbidden.
The options, cheapest first:

1. **An explicit harness opt-out.** Let `storage()` accept the local driver in production when a flag
   only the e2e config sets is present (`E2E_ALLOW_LOCAL_STORAGE=1`). One greppable hole, set in one
   place, and the guard keeps refusing a real deployment. Touches `src/server/storage/index.ts`,
   `src/env.ts` and `playwright.config.ts`.
2. **Run the stack as `NODE_ENV=test`.** One line, but it moves far more than storage — `t()` throws
   on a missing key outside production, error pages change, and the suite stops testing what a
   production build does.
3. **Leave it.** Then no e2e can ever exercise media, and that bill comes due again in Phase 4 (PWA
   icons are generated through the same pipeline) and Phase 5.

Recommend 1. It is also the only one that keeps the e2e suite testing the artefact that ships.

## Findings raised, not fixed — they live in forbidden or other-track files

### 8. Three pack config keys are silently stripped by the site contract

`src/shared/site-contract/sections.ts` strips unknown keys by design, and three keys the frozen packs
write are not the contract's names for the same thing:

| pack key | contract key | consequence if stored verbatim |
|---|---|---|
| `hero.cta` | `ctaLabel` | every hero renders the generic `st('hero.cta')` instead of «اطلب عبر واتساب» |
| `contact_whatsapp.note` | `body` | the contact block loses «رد سريع خلال ساعات الدوام» |
| `products_grid.showBadges` | *(none)* | inert — badges render unconditionally from `Product.badge` |

Both the packs and the contract are frozen to this track, so the adaptation lives in the consumer:
`src/server/demo/sections.ts` aliases the first two before validating, and drops the third. A unit
test pins the pack's own Arabic onto the contract keys so the mapping cannot rot.

**Open question for the main session:** `hero.ctaHref` was deliberately NOT invented. All three pack
CTAs say "order / request a quote by WhatsApp" and the renderer's default href is `/products` — so
the label points at a product list rather than at the contact block. Pointing it at
`#${SECTION_ANCHORS.contact_whatsapp}` would match the label but duplicate the ghost button the hero
already renders beside it. That is A2's UX to decide, not B3's, so the default stands.

### 9. `products_grid.columns` — a schema default that silently overrides three template designs

`columns` has `.default(3)`, and `ProductsGridSection` reads `config.columns ?? template.layout.gridColumns`.
So a *parsed* config always carries a value and the template's own grid is unreachable: warsheh's four
dense columns and neon-souq's two large ones would never render, on three packs that are already
structurally identical (same seven section types, same order, same `chips` category style).

B3 tried to work around it by dropping the defaulted key before storing the row, and that was WRONG —
worth recording so nobody rebuilds it. `normaliseSectionConfig` in `src/templates/lib/section-config.ts`
re-parses the stored config on every read, so the schema default is re-applied at render time no
matter what the row contains. The workaround was a no-op with moving parts, and it has been removed;
`src/server/demo/sections.ts` carries the note in its place.

The only real fix — the schema not defaulting a field whose absence is meaningful — belongs in
`src/shared/site-contract/sections.ts`, which is forbidden here. `gallery.columns` has the same shape,
and so does anything else a renderer reads as `config.x ?? template.y`.

### 10. A custom colour selection collapses `surface` onto `background`, for every tenant

`resolveColors` sets `surface = selection.surface ?? selection.background`, and A2's
`resolveTenantColors` re-runs it on every read. So any tenant on custom colours gets a surface equal
to their page background — the tinted `derivedSurface` in `src/templates/tokens.ts` is unreachable
whenever a `ThemeSettings` row exists. For the food pack that is white cards (#FFFFFF) turning cream
(#FAF3E7): every panel stops being a panel.

B3 sidesteps it rather than fixing it, because each pack's three colours turn out to be **exactly one
of the five vetted presets** (clothing → ليلي, industrial → فولاذ, food → صحراء). The builder matches
by colour and stores `colorMode: 'preset'`, which carries all five tokens. A unit test asserts the
match still holds and that each preset's surface differs from its background, so the day a pack drifts
the fallback is loud rather than a demo that quietly flattens.

The underlying interaction is unchanged and affects merchants too. It lives in `site-contract`.

### 11. The demo magic token is copied into a global table and POSTed to n8n

`createDemo` emits `demo.created` with `demoUrl: demoStorefrontUrl(slug, token)` in the payload
(`src/server/billing/index.ts:1114-1122`), and emitting an event materialises its `WebhookDelivery`
rows — which are GLOBAL and therefore survive `closeDemo`. So the demo's bearer token, and the
prospect's slug with it, end up in a table the purge does not reach and in whatever n8n keeps.

`tests/unit/guardrails.test.ts` already forbids exactly this shape for the export link ("a presigned
URL in an n8n execution record is a working key to a merchant's catalogue sitting in a backup"). A
demo token is worth much less — after the demo closes it resolves to nothing, and while it is open it
opens a shop the platform built — so this is a smaller version of a rule the platform already made,
not a new one. `src/server/billing/**` is forbidden here; the fix is to carry `slug` and let the
consumer compose the URL, or to omit the token as the export path does.

### 12. `admin.events.*` / `admin.actions.*` are unreachable through `t()`

`messages/ar/admin.json` stores those groups as FLAT dotted keys (`"demo.created"`), and
`resolve()` in `src/shared/i18n` splits on `.` and walks the tree — so `t('admin', 'events.demo.created')`
can never resolve. Verified against the real resolver; A1's own `actions.plan.created` is affected
too. Consequence for B3: the audit table renders the raw identifier `demo.created` for every row this
track writes. `messages/ar/admin.json` is A1's — nesting those keys is a main-session change.

## Decisions

### The B1/B3 seam: the content builder writes media itself

`src/server/billing/demo-content.ts` hands the builder an **already-open transaction** and expects an
`afterCommit` callback. A3's `ingestInternalImage()` — documented as "B3's door" — cannot be used from
inside it: it opens its own `withTenantTxn` and enqueues immediately, which would take a second
connection per product, commit fifteen `Media` rows independently of the catalogue they belong to, and
fire fifteen jobs before the demo exists.

So `src/server/demo/images.ts` assembles the same operation from A3's exported primitives —
`sniffIngestible`, `mediaSourceKey`, `mediaStorage`, `resolveStorageLimits`, `admitUpload`,
`readTenantStorageBytes`, `adjustTenantStorageBytes` — writes the rows on the caller's `tx`, and
returns the enqueue as `afterCommit`. Nothing is added to A3's folder and a demo's images are
indistinguishable from an uploaded one, so the library, the purge and the orphan sweep all understand
them.

Two refinements over a literal transcription of `upload.ts`:

- **one locked read, one quota update.** `readTenantStorageBytes` is `SELECT … FOR UPDATE` on the
  tenant row; taking it fifteen times inside one transaction re-locks what we already hold. The
  admission check runs against a running total instead, which is the same guarantee for a
  single-writer build.
- **the objects are taken back on failure.** `createDemo`'s catch deletes the tenant, so nothing would
  ever look under that prefix again and A3's orphan sweep would be the only collector. `discardObjects()`
  removes them immediately; the sweep stays a backstop rather than the strategy.

**Accepted risk:** if the `afterCommit` enqueue fails, the demo has already committed and
`upload.ts`'s rollback shape is unavailable. The `Media` rows stay `pending`, the demo renders
placeholder letters, and A3's cleanup is what eventually notices. Rolling the demo back over a
broker blink would be worse — the shop is correct and the operator can see the pending count on the
detail screen.

### `src/server/demo/seed-assets/`, not a repository-root `seed-assets/`

The pack README writes the real-photo path as a bare `seed-assets/{pack}/{sku}.*`, but a top-level
folder is outside every track's ownership in `scripts/check-track-ownership.ts` — creating one would
be a violation on the branch that adds the first photograph. The lookup lives inside the folder B3
owns; the addressing (`{pack}/{sku}.{ext}`) is unchanged.

It is allowed to be absent and it is absent today, which is what the pack contract already says
("a real file if one exists, otherwise a generated SVG"). Every failure — no directory, no file, an
unreadable file, a bundle that traced no photos — resolves to the placeholder. **When real photos are
added, `next.config.ts` needs an `outputFileTracingIncludes` entry** or the Next standalone build will
silently keep drawing placeholders.

One thing for the main session to reconcile: `.gitignore` already carries
`seed-assets/**/*.{jpg,png,webp}`, so a repository-root folder WAS anticipated somewhere — but
`scripts/check-track-ownership.ts` has no entry for it, and those patterns are unanchored so they
match the path chosen here too. If the root location is the intended one, the ownership table needs a
line for it; otherwise the `.gitignore` comment is the thing that is out of date. Either way the
photos themselves stay untracked, which is the part that matters.

### Slug is the SKU; price is agorot

`Product.slug` is NOT NULL, unique per tenant, and lands unencoded in `/products/{slug}`. The packs
carry no slug and slugifying an Arabic name yields an empty string, so the SKU — already ASCII and
already unique within a pack — is used for both `sku` and `slug`. Pack prices are whole shekels
(`189`) and the column is `price_agorot`, so ×100 with `Math.round`; a unit test asserts every pack
price converts exactly.

### The home page is B3's to create

`Section.pageId` is NOT NULL and `createDemo` writes no `Page`. The storefront loads sections only
through `page.slug = 'home', published: true` — so a demo without that row renders as a site with no
sections and no error at all. The builder creates it with `isSystem: true`, matching A1's
`seedDefaultSections`, so it is not deletable from the merchant side after a conversion.

### `Site.sellingEnabled` stays false

`createDemo` does not set it and neither does the builder. A demo is a WhatsApp-order showcase with no
checkout, so the returns/cancellation policy and the permanent «إلغاء معاملة» footer link would be
promising a transaction that cannot happen. Revisit in Phase 5, with payments.

### The public form checks the prefix against tenants only

`app_web` has INSERT and no SELECT on `demo_requests` outside a super admin, so the form cannot ask
whether another PENDING request already claimed a prefix — and widening that policy to answer a
stranger would expose every other prospect's choice. Uniqueness is therefore checked against
`tenants.slug` (which `tenant_hostname_lookup` legitimately opens pre-context, because a slug is a
hostname and already public), and two requests for one word are resolved in the inbox, where the
prefix is editable at approval time.

### The rate limit fails OPEN

`src/server/demo/rate-limit.ts` mirrors A3's two-layer shape: a Redis counter with an atomic
INCR+EXPIRE, and an in-process window when Redis is unreachable. Failing closed was considered and
rejected — a cache blink would silently reject every sales lead the platform has, with an Arabic
apology, and nobody would find out until someone asked why the inbox was empty. The in-memory window
still binds, `DEMO_REQUEST_RETENTION_DAYS` still bounds what survives, and the form still creates no
tenant. Flooding it costs an attacker an inbox to reject.

The limit is charged BEFORE validation and before any read: a limiter that only counts well-formed
submissions is not a limiter.

### The public action returns resolved Arabic, not message keys

Every other action in the platform returns an i18n key and the client component resolves it. This one
resolves on the server, and the client form imports no i18n at all. `src/shared/i18n` is a static
object of all seven namespace files, so one `t()` in the `'use client'` form would ship the admin
panel's entire message catalogue to a prospect on a phone. Behind a login that is a fair trade; on
the one page the platform serves to the open internet it is not. The copy still lives in
`messages/ar/demo.json` where the language gate can see it — only the resolution moved.

### `/demo-request` is guarded to the app surface

The path is unprefixed by design (it is on a business card), which also means it renders on any
hostname the proxy resolves — including a merchant's storefront. The page reads the surface the proxy
already decided and 404s anything that is not `app`, so a platform sales form never appears under
someone else's shop name.

### `(public)` carries `data-surface="public"`, not `"app"`

`dashboard.css` is scoped to `[data-surface='app']` and is a global stylesheet once bundled, so
reusing that value would pull the dashboard's chrome onto a page that has no dashboard. The public
tree has its own small stylesheet and its own single `<main id="main">`.

### `demo/build-demo` stays a loud failure

Phase 1 registered the queue path so B3 could add a processor without editing a shared file. B3 does
not need one: the demo must be built inside the transaction that creates it, and the only
asynchronous part — image variants — already has A3's `media` queue. The processor therefore throws
with an explanation rather than being deleted, because `src/server/queues.ts` is forbidden and a
silently-succeeding processor would hide a job nothing in the codebase creates.

### The pack label lives in the catalogue

`pack.label` and `demo.packs.{key}` are the same string in two places and had already drifted
(«مواد بناء ومعدات» in the catalogue vs «عدد ومواد صناعية» in the pack). The pack is frozen, so the
catalogue follows it, and a unit test asserts they stay equal.

### The demo list reports the TEMPLATE, not the pack

The pack a demo was built from is not stored on the tenant — `createDemo` takes a `packKey` and writes
what the pack says without recording which pack said it. A demo from the public form can be matched
through its originating `DemoRequest`; everything else is reported by its template name rather than by
a guess. A `Tenant.demoPackKey` column would be the honest fix and is a migration, so it belongs to
the main session.

## Running the e2e suite inside a worktree

`pnpm e2e` cannot run from `sb-b3` as the worktree is set up: its `node_modules` is a Windows junction
to the main checkout's, and Turbopack refuses it outright — *"Symlink [project]/node_modules is
invalid, it points out of the filesystem root"* — so `pnpm build`, and therefore Playwright's
`webServer`, dies before a test runs. It is not a property of this branch; any worktree hits it.

`next build --webpack` compiles the same tree without complaint, so the suite was run through a
throwaway config at `.tmp/pw-b3.config.ts` (gitignored, inherits the real one, swaps only the build
command):

```
node node_modules/playwright/cli.js test --config .tmp/pw-b3.config.ts b3-demo
```

It has to live inside the repository rather than in a scratch directory: Playwright loads a config
outside the package as CommonJS, and `tests/e2e/support/env.ts` uses `import.meta.url`. At merge time
in `main` — a real checkout with a real `node_modules` — plain `pnpm e2e` works and this is unnecessary.

The `webServer.command` also invokes its tools through `node …/dist/bin/next` rather than `npx`,
which was a workaround for a separate and now-fixed problem: the shared `node_modules` had lost the
contents of several packages (`esquery`, `magic-string`, `astring` were all empty directories behind
live symlinks), so `eslint` and `vitest` refused to start mid-session. `pnpm install --force` from
the main checkout repaired it and every gate below ran afterwards. Worth knowing if the same
`Cannot find module 'esquery'` appears again — it is the store, not the branch.

One e2e case is worth watching for flakiness: `a submitted request creates no tenant, and reaches the
admin inbox` failed once at the admin sign-in step (`نظرة عامة` not visible within Playwright's 5s
expect timeout) on a cold server, and passed on every other run. If it recurs in CI the sign-in helper
wants an explicit longer timeout rather than a retry.

## What the gates say

- `pnpm typecheck`, `pnpm lint` — clean.
- `pnpm test` — 41 of 43 files pass. The two failures are sync points 1 and 2 above: A1's and B1's
  own placeholders asserting that B3 had not landed. Every B3 file is green
  (`tests/unit/b3-demo-packs.test.ts` 53, `tests/unit/b3-demo-request-limit.test.ts` 7,
  `tests/integration/b3-demo.test.ts` 13).
- `pnpm e2e` (via the worktree config above) — 4 pass, 3 skipped on sync point 6.
- `npx tsx scripts/check-track-ownership.ts b3 .` — clean, all 26 changed paths inside B3's
  ownership. `TODO.md` is deliberately NOT ticked: the checker forbids it to every track
  ("three tracks appending to one checklist is a conflict per track per commit"), and the main
  session ticks it at merge from the branch it just reviewed.
- The acceptance clock: `createDemo` for a 15-product pack, including SVG generation, magic-byte
  sniffing, storage writes and every row, completes in **~3 seconds** against a local cluster. The
  30-second criterion is about the link, which is minted in the same transaction; the image VARIANTS
  arrive afterwards through A3's queue, and the detail screen shows the pending count so an operator
  knows whether to wait.
