# A3 — Media pipeline

Implementation decisions taken while building the media pipeline. Folded into
`docs/DECISIONS.md` at merge review.

Scope: `src/server/media/**` (including `storage/` and `processors/`),
`src/app/api/media/**`, `messages/ar/media.json`, `tests/**/a3-*.test.ts`.

Several notes below record a decision that was WRONG in an earlier pass and has been corrected.
They are kept as corrections rather than rewritten away, because they were all wrong in the same
way — an invariant that looked satisfied because nothing tested it. The largest of them is sync
point 3, which an earlier draft WITHDREW on reasoning that was simply mistaken; it is restored at
the bottom of this file and is a merge blocker.

---

## The storage driver

- **The R2 driver is the only file in the codebase that imports the S3 client.** It lives at
  `src/server/media/storage/r2-driver.ts`, which is the path both `eslint.config.mjs` and
  `tests/unit/guardrails.test.ts` already single out. Everything else — B1's purge, B2's library,
  the Phase 1 export route — talks to `StorageAdapter`.
- **The S3 client is built on first use, never at import.** A module that opens a client at
  import time makes every unit test and every build step depend on credentials existing. The
  adapter can be constructed with no configuration at all; it only complains when someone
  actually asks it to move bytes.
- **`registerMediaStorage()` deliberately does NOT call `storage()` when the driver is local.**
  Returning "the adapter now in force" was the obvious signature, and it was wrong: it would
  materialise the local driver as a side effect of an import, and in a production deployment
  misconfigured to `STORAGE_DRIVER=local` it would turn a clear runtime refusal into a module
  that throws while being imported.
- **`deleteByPrefix('')` throws.** An empty prefix is the whole bucket — every tenant at once. The
  callers all build their prefix with `tenantPrefix()`, but the one that eventually does not is
  the one that matters, and the cost of the guard is one comparison.
- **`deleteByPrefix` READS the per-key `Errors` and raises when a prefix did not empty.** This was
  the worst correctness bug in the driver and it was invisible: `DeleteObjects` is a
  partial-success API — it answers HTTP 200 and reports failed keys in an `Errors` array, so the
  SDK throws nothing. Counting `batch.length` as removed meant the driver reported a clean sweep
  over objects that are still there, and the caller that matters is B1's purge: it would write its
  audit row, delete the Tenant row, and leave product images fetchable unsigned from the public
  media prefix, for a merchant whose data the platform had just certified as erased. `Quiet` is now
  `false` deliberately (quiet mode suppresses exactly that array), the count excludes failures, and
  a prefix that did not empty raises with the surviving keys named. The in-memory fake now models
  partial failure, because a fake that only ever succeeds cannot test the path that matters.
- **A bucket-level 404 is NOT "the object is absent".** `NoSuchBucket` also arrives as HTTP 404, and
  `isNotFound()` swallowed it. The consequence was specific and bad: `process-upload` asks
  `exists()` before deciding whether a source is genuinely gone, so a web container writing to one
  bucket and a worker reading from another (a typo in `R2_BUCKET`, or a rename applied to one side
  first) marked every upload `sourceMissing` — permanent, never retried — and told the merchant
  «ما لقينا ملف الصورة الأصلي» about an object sitting safely in the other bucket. On a fresh
  deploy that is 100% of uploads.
- **`R2_SSE_ALGORITHM` is checked against an allow-list, not cast.** `src/env.ts` validates it as a
  string, so `AES-256` (for `AES256`) costs nothing until the first write that asks for encryption
  — which is the suspension export, the one artifact whose loss is unrecoverable and whose absence
  the merchant discovers only after being promised thirty days. The check runs OUTSIDE `put()`'s
  try, or the catch-all would rewrite the refusal as "Failed to store object" and throw away the
  sentence naming the variable. A test caught that; the first version of this fix had the bug.
- **`publicUrl()` requires an ABSOLUTE base.** `CDN_PUBLIC_BASE_URL=cdn.souqbartaa.com` — a missing
  scheme, the most ordinary deploy typo there is — made every `<img src>` a RELATIVE path, so every
  storefront asked its own hostname for `/cdn.souqbartaa.com/tenants/…`. No exception and no log
  line: just broken images everywhere and every image request landing on the origin the CDN exists
  to protect.
- **`publicUrl()` on the R2 driver refuses to fall back to the app server when
  `CDN_PUBLIC_BASE_URL` is unset.** A fallback would break invariant 4 in production while
  looking like it worked. The local driver keeps its dev-media fallback, because that is the
  whole point of the local driver.
- **The SigV4 ceiling is stated in the driver as `SIGV4_MAX_TTL_SECONDS = 604800`** next to a
  clamp that never lets a URL past `MAX_SIGNED_URL_TTL_SECONDS` (one hour). A unit test asserts
  both, so nobody can quietly raise the platform limit toward the protocol limit and rediscover
  Q18 the hard way.

## Object layout

Keys are built only from `mediaPrefix()`, never by hand, and the layout is one folder per item:

```
tenants/{tenantId}/media/{mediaId}/source.jpg    the upload — discarded after processing
tenants/{tenantId}/media/{mediaId}/thumb.webp    400
tenants/{tenantId}/media/{mediaId}/card.avif     800
tenants/{tenantId}/media/{mediaId}/full.webp     1600  <- Media.key once ready
```

- **The `{mediaId}` segment is what makes orphan cleanup exact and cheap.** An object is an orphan
  when its media id has no `Media` row: one set-membership test per object rather than a query
  per object.
- **A KIND is not the same thing as an OBJECT: several variant rows may name one key.** `resize`
  runs `withoutEnlargement`, so a source narrower than a target is never upscaled — a 240px photo
  produced thumb, card and full as three byte-identical objects, six across both formats, every one
  of them billed against `storage_mb`. On a 500MB أساسي plan that is a third to a half of the quota
  spent on duplicates the CDN would never serve differently, and the common case is not exotic: any
  already-resized 800px product photo made `card` and `full` identical. The processor now renders
  one object per distinct effective width per format and points the redundant kinds at it. Two
  consequences worth stating for A2 and B2, since both build on this shape:
  - every `(kind, format)` pair still has a `MediaVariant` row, so `variants.find(kind === 'card')`
    keeps working and no consumer needs to learn a new shape;
  - **summing `MediaVariant.sizeBytes` is NOT the item's footprint.** Each row carries the true size
    of the object it names, and several rows may name one object. `Media.sizeBytes` is the
    authoritative total and counts each object once.
  The representative of a group is always its WIDEST kind, which is what keeps `full.webp` a real
  object — `Media.key` points at it and `loadSource()` recovers from it.
- **`Media.key` moves.** It points at the source object while the item is pending, and at
  `full.webp` once it is ready. The alternative — keeping it on a source object that invariant 4
  requires us to delete — leaves every ready row pointing at something that does not exist.

## The upload path

- **Both plan limits are checked twice: once before a byte is written, once inside the
  transaction that reserves the quota.** The early check is what stops an over-limit file from
  being uploaded to R2 and only then refused (bandwidth the limit exists to protect, and a
  billable write).
- **The transactional re-check reads the tenant row `FOR UPDATE`, and that lock is the whole
  point.** An earlier version of this note claimed the re-check on its own closed the
  concurrent-upload race. It did not, and the distinction is worth writing down because it looks
  like a detail: the atomic `GREATEST(0, used + delta)` update prevents a LOST increment, not
  over-ADMISSION. Under READ COMMITTED both transactions read the same pre-image, both admit, and
  both then apply their delta — the account lands over `storage_mb` by up to N x `image_max_mb`.
  `SELECT ... FOR UPDATE` serialises read-decide-reserve on the tenant row, so the second upload
  waits for the first to commit and then sees a value that includes it. There is now a
  concurrency test that fails without the lock (two 4MB uploads into 6MB of quota: exactly one is
  admitted).
- **A missing feature value fails CLOSED.** `can()` returns the stored value as-is, so
  `undefined` for `image_max_mb` means we could not establish what this tenant is entitled to —
  not "unlimited". (This is the opposite of `change_requests_per_month`, where a stored `null` is
  a real answer meaning unlimited. Absent and null are different, and the code distinguishes
  them.)
- **Both refusals name the number.** `errors.fileTooLarge` carries the file size AND the plan's
  per-file limit; `errors.storageFull` carries the quota, how much of it is LEFT, and what this
  file needed. The per-file check runs first, so a merchant with one oversized photo on a full
  account is not sent to delete images they did not need to delete.
- **Every number in one sentence uses ONE byte convention.** This was got wrong the first time and
  the failure was invisible in isolation: `{limit}` came from `formatPlanMegabytes()` (the plan's
  own convention, 1GB = 1000MB) while `{used}` and `{size}` came from `formatBytes()` (1GB =
  1024MB). A tenant on the 3000MB plan with 3MB of real headroom was refused with «مساحة التخزين
  في باقتك 3 غيغابايت، ومستعمل منها 2.9 غيغابايت. هذه الصورة بدها 5 ميغابايت وما بتسع» — the
  merchant reads roughly 100MB of free space and a refusal, and opens a ticket. `fileTooLarge` had
  the same artifact: 10.04MiB on the 10MB plan rendered as "حجم الصورة 10 ميغابايت، والحد المسموح
  10 ميغابايت". Both ends now go through `formatMegabytes()`: `formatPlanMegabytes(mb)` for a plan
  number and `formatStorageBytes(bytes)` for a real count. `formatBytes()` from the i18n layer is
  still correct elsewhere; it is simply never put next to a plan number.
- **Free space rounds DOWN and a required size rounds UP.** Otherwise a 4.64MB gap and a 4.62MB
  photo both render "4.6 ميغابايت" and the refusal reads as nonsense. The message also names what
  is LEFT rather than what is used — "you have 3 ميغابايت free and this needs 5" is something a
  merchant can act on; "you have used 2.9 of 3 غيغابايت" is arithmetic they have to do themselves.
- **A failed enqueue rolls the whole upload back** — object, row and reservation. A `Media` row
  with no job behind it is a tile that says "قيد المعالجة" forever and quota the merchant cannot
  get back.
- **`Media.failureReason` stores a CODE, not a sentence.** The column outlives any copy change,
  and a merchant must never be shown a raw English string from a worker;
  `mediaFailureMessage()` turns it into Arabic from `messages/ar/media.json`.

## SVG

- **Uploaded vector documents are refused with their own error code, not lumped into
  "unsupported".** They have no magic number, so they are sniffed as markup. The merchant gets
  the real reason (it can carry executable markup, and it would run on the storefront's own
  origin once the CDN served it) instead of a generic shrug.
- **`ingestInternalImage()` is the platform's own door and accepts them.** B3's demo placeholders
  are generated SVG (`src/server/demo/placeholder.ts`) and must reach the same pipeline. There is
  no HTTP route into that function and there must not be one: the reason uploaded vectors are
  refused is that they came from outside.
- **Rasterising platform SVG relies on librsvg's system fonts.** The Dockerfile already installs
  `fonts-noto-core`; without it Arabic text in a generated placeholder renders as boxes.

## Processing

- **The processor is idempotent.** A ready item short-circuits; a partial run is overwritten,
  because variant keys are deterministic and `MediaVariant` rows are replaced wholesale.
- **Storage is resolved with `mediaStorage()`, never a bare `storage()`.** This is the fix for the
  worst bug in the track and it is worth stating as a rule rather than a patch. The R2 driver used
  to be installed only as an import side effect of `src/server/media/index.ts`, and the worker
  never imports that barrel: `src/worker/index.ts` -> `@/server/queues` -> the lazy path
  `./media/processors/process-upload`, whose imports never reach it. So with `STORAGE_DRIVER=r2`
  the registry threw "no R2 adapter is registered" on the first `get()` — inside the `try` whose
  `catch` converts ANY failure into a PERMANENT `sourceMissing`. The job COMPLETED, the row was
  marked `failed`, the merchant was told «ما لقينا ملف الصورة الأصلي» about an object that was
  sitting in R2, the reserved quota was never released, and nothing retried. On a fresh production
  deploy that is 100% of uploads. Anything under `src/server/media` that touches objects now goes
  through `mediaStorage()`, which registers and then answers; a unit test reads both processors
  and fails if either imports the registry accessor directly.
- **Permanent failures are recorded, transient ones are re-thrown — and the two are now actually
  distinguished.** `sourceMissing` means the object is genuinely not there, established with a
  HEAD, not "the first call to storage failed for any reason". Every driver funnels its failures
  through `StorageError`, so an unconfigured driver, an expired credential and a deleted object
  all arrive looking identical; treating that whole class as permanent is what turned a
  configuration mistake into a lie told to every merchant. A file that will not decode still will
  not decode on the fifth attempt, so `decode` stays permanent.
- **A run whose transaction never commits is recoverable.** The original has to be discarded
  before the commit — `src/server/queues.ts` opens the transaction around the whole processor and
  is a frozen shared file, so there is no post-commit hook to hang the delete on, and it is not
  transactional in any case. When that commit then fails, the rows roll back to `pending` and the
  bytes do not come back. `loadSource()` closes it: the retry falls back to `full.webp`, which the
  dead run wrote before it deleted anything. That costs one WebP generation and a 1600px cap —
  the widest variant the platform keeps anyway — instead of losing the photo and stranding six
  objects that no sweep would ever collect (their `Media` row still claims them).
- **EXIF is applied and then dropped.** `.rotate()` with no argument consumes the orientation tag;
  sharp writes no other metadata unless asked. A product photo taken on a phone carries GPS
  coordinates, and these variants are served from a public CDN.
- **The recorded dimensions are the ORIENTED ones.** Because `.rotate()` applies the orientation,
  a photo stored 1200x900 with EXIF orientation 6 renders 900x1200 while `metadata.width/height`
  still reports 1200x900 (measured on sharp 0.35.3 here; `metadata.autoOrient` reports the pair
  correctly and was being ignored). Recording the container's numbers put every portrait phone
  photo in the database as landscape, disagreeing with its own variant rows, so anything sizing an
  `<img>` box from `Media.width/height` reserved 4:3 for a 3:4 image — a layout shift on every such
  photo, against a stated budget of CLS < 0.1.
- **The pixel ceiling is OURS, named, and 40MP.** sharp refuses past `limitInputPixels` from
  `metadata()` onward, and that refusal is indistinguishable from a corrupt file — so a 17000x17000
  flat scan, which encodes to about 1.6MiB and therefore passes the 25MB envelope AND the 2MB
  أساسي per-file limit, died in the worker and told the merchant «ما قدرنا نقرأ الصورة، يمكن الملف
  تالف» when the real remedy was to reduce the dimensions. `failure.tooLarge` already had the right
  Arabic sentence and no way of ever being reached. The header is now read with the limit off
  (parsing a header allocates no pixels — 1ms on that file) and the ceiling enforced explicitly.
  40MP rather than sharp's 268MP because the number has to be one the worker can hold: PNG has no
  shrink-on-load, so a 10000x10000 PNG is 400MB of raster, and `concurrency: 2` means two at once.
  Past the container's limit the OOM killer takes the worker down mid-transaction and BullMQ
  re-delivers the same job to the restarted worker — one upload becomes a poison pill that kills
  every other media job with it, on every retry. `sharp.cache({memory: 64})` and
  `sharp.concurrency(1)` bound libvips for the same reason.
- **A permanent failure releases the quota AND the bytes.** It used to leave the tenant charged for
  the upload forever: the item stores nothing usable, the orphan sweep will not touch it (a `Media`
  row exists, so its objects are not orphans), and the only way back was for the merchant to notice
  a failed tile and delete it by hand. Worse for `sourceMissing`, where we had just PROVEN the bytes
  are gone and went on charging for them. The processor now deletes every object the item could own
  — the source plus any variants a run wrote before dying partway through — zeroes `sizeBytes`, and
  hands the bytes back.
- **`Media.key` moving is claimed atomically.** The ready-check used to be a read followed by an
  update, and BullMQ is at-least-once: a stalled job is re-delivered while the first run is still
  going, both read `pending`, the second blocks on the first's row lock and then continues with the
  values it read BEFORE the first committed — applying `storedBytes - sizeBytes` a second time and
  driving the tenant's counter down by the original upload size twice. A conditional `updateMany`
  takes the lock and decides in one statement; every value used afterwards is read after it.
- **A missing row is not an error.** Deleting a pending tile before its job runs is ordinary, and
  throwing made BullMQ retry a condition the code itself calls permanent — five attempts and a
  dead-lettered job per deleted item, so a merchant clearing forty uploads produced two hundred
  failing attempts. That is exactly the signal an operator watches to spot a real outage.
- **Media is cached for a day, not a year.** `max-age=31536000, immutable` is the right header for a
  content-addressed asset and the wrong one here: a merchant who uploads a photo that happens to
  show a customer's ID card, notices, and deletes it has the row and the objects removed while the
  published URL keeps serving from the edge for up to a year, because `immutable` tells the cache
  never to revalidate. The same gap outlives B1's purge. A day of freshness with a week of
  `stale-while-revalidate` keeps the edge answering instantly and bounds the exposure to something
  the privacy copy can state honestly. Purging the edge on delete is the complete fix — sync point 4.
- **`Tenant.storageBytesUsed` is adjusted with one SQL statement**
  (`GREATEST(0, used + delta)`), never read-modify-write. Concurrent uploads would otherwise lose
  an increment — a quota that leaks quietly, in exactly the busy account where it matters. The
  counter holds the upload size while pending and the sum of the variants once ready, so it
  reflects what is actually stored rather than what was sent.

## Orphan cleanup

- **`_exports/` is skipped, checked first, via `isExportKey()`.** Those objects are owned by
  `src/server/billing` and have no `Media` row by design. This is written now, before B1 exists,
  because its author would otherwise have no reason to suspect a sweep was already walking their
  prefix — and the failure mode is deleting a suspended merchant's only copy of their catalogue
  in the middle of a retention window the platform promised was a month long.
- **The FAN-OUT comes from the database; the bucket scan only finds rowless prefixes.** Both halves
  matter and the first was wrong. Deriving the tenant list from a key listing capped at 100k meant
  that at roughly a hundred merchants (one processed image is several objects) the scan stopped
  mid-bucket in S3 lexicographic order — and cuid ids ascend with creation time, so it was always
  the NEWEST tenants that fell off the end, silently and permanently, every night. A tenant with no
  objects at all was skipped for the same reason, which is precisely the tenant whose abandoned
  uploads need reclaiming. The listing still answers the question only storage can answer — which
  prefixes have no row — and now says so out loud when it was truncated.
- **A rowless prefix is swept only when a `TenantTombstone` proves a purge happened.** This is the
  most dangerous code in the track and the guard it had was not enough. `app_system` + "at least one
  live tenant" only catches a TOTAL read failure. Consider the restore runbook Q10 requires: the
  database comes back from a 14-day-old dump while R2, which is not restored, still holds
  everything. Every tenant created inside those 14 days now has objects and no row — the role is
  right, hundreds of tenants are live, every prefix is long past its grace window — and the old
  rule would have deleted all of their product images and their `_exports/` artifacts at 04:00 that
  night, unrecoverably, because originals are discarded by design. Absence of a row is the one
  signal a broken or stale read produces for free. A tombstone is POSITIVE evidence, it is global
  so it survives its own tenant, and `app_system` already has SELECT on it. Until B1 ships and
  starts writing them, no rowless prefix is swept at all — which is the correct failure direction.
- **Two grace windows.** An object younger than one hour is left alone (the upload writes the
  object before it commits the row). A prefix with no tenant row waits a full day before being
  swept wholesale — a purge that is merely slow must never be mistaken for one that finished.
- **Unrecognised key shapes under a tenant prefix are logged and left — and "unrecognised" now uses
  the same predicate as "interpreted".** `isMediaKey()` only asks whether a key sits under `media/`;
  `mediaIdFromKey()` is what understands the layout. Testing the first and acting on the second
  meant anything under `media/` that was not exactly `{mediaId}/{file}` came back with a null id,
  read as "nothing owns this", and was DELETED an hour after it was written: a zero-byte directory
  marker from the R2 dashboard or `rclone --s3-directory-markers`, a flat `media/logo.png`, or any
  future layout with one more segment. The guard that exists to stop us guessing at an unknown
  owner never fired, because the key had passed a prefix test rather than a shape test.
- **An object whose age cannot be established is never deleted.** `isOlderThan(undefined)` answered
  `true`, which silently disabled BOTH grace windows for any adapter that leaves `lastModified` off
  a listing — the field is optional on `StoredObject`, and a gateway, a double or a cheaper listing
  path may legitimately omit it. With it absent, a source object written seconds ago (the upload
  writes the object before it commits the row) is "old enough", and a rowless prefix skips its full
  day of grace. Both failures delete data on the strength of a field nobody set.
- **Deletes are capped per run, and what was deferred is reported.** The processor runs inside the
  120s Prisma transaction `src/server/queues.ts` opens, and deleting is one round trip per object,
  so a tenant with a few thousand orphans spent longer than the budget, had its transaction
  cancelled with P2028 after doing most of the work, was retried five times and finally
  dead-lettered — reporting failure on every run while quietly making progress. The sweep is daily
  and idempotent, so a cap converges over a few days. `deferred` is in the summary and logged:
  a bounded run must never read as a complete one.
- **Uploads abandoned mid-processing get their quota back.** BullMQ gives `process-upload` five
  attempts over ~75 seconds; an outage longer than that exhausts them while the failure is still
  transient, the row rolls back to `pending`, and the job leaves the queue for good. Nothing then
  owns the item — the tile reads «بانتظار المعالجة» forever and the tenant keeps paying for it. The
  sweep is the only thing that walks every tenant, so it marks anything stuck past 24h as `failed`
  and releases the bytes. Deliberately NOT a re-enqueue: re-queueing something that already burned
  five attempts is how a retry storm starts, and a merchant is better served by a tile that says so.
- **A `failed` item's source counts as an orphan.** This one was introduced by the fix above and
  caught in review: once `releaseStuckMedia` marks a row `failed` with `sizeBytes: 0`, the row still
  EXISTS, so the source object was no longer an orphan by the "no row" test and nothing would ever
  collect it. The platform would stop charging for those bytes and go on storing them forever —
  the worst of both. The predicate now covers `ready` and `failed`.
- **The fan-out is enqueued at an explicit low priority.** BullMQ documents `priority: 0` as "no
  explicit priority" and takes unprioritized jobs BEFORE prioritized ones, so giving cleanup a
  positive number puts a nightly janitor permanently behind interactive work. Without it, 300
  cleanup jobs land at 04:00 on a queue with concurrency 2 and the next merchant to upload a photo
  watches «قيد المعالجة» until the sweep drains.
- **The system half has two guards the tenant half does not need.** `sweepTenantOrphans` is
  fail-safe by construction: it reads through RLS, so a bug pointing it at the wrong tenant sees
  an empty set and deletes nothing. The system half has the opposite shape — it infers "purged"
  from the ABSENCE of a row and acts on that with `deleteByPrefix`, media and `_exports/`
  together, unrecoverably. Absence is the one signal a broken read produces for free. So the
  destructive half now refuses to run unless (a) `current_user` is `app_system` — `env.ts` has
  `DATABASE_URL_SYSTEM` as `.optional()` with a fallback to the app_web URL, so "the system client
  is not really app_system" is one missing variable away — and (b) it found at least one live
  tenant. Fan-out is unaffected either way, since dispatching a per-tenant sweep is safe on its
  own. Measured, not assumed: with `DATABASE_URL_SYSTEM` unset the read does NOT come back empty
  (the `tenant_hostname_lookup` policy in migration `20260809000100` is permissive and matches
  when no `app.tenant_id` GUC is set, so app_web with no context sees every tenant row) — but a
  destructive cross-tenant sweep should not be relying on the exact shape of an unrelated
  pre-context policy to stay safe.
- **The schedule is an UPSERT keyed on its id, not `add({ repeat, jobId })`.** BullMQ derives a
  repeatable's key from a hash of name, jobId, endDate, tz AND pattern, so the id alone only dedupes
  while the pattern never changes. Tighten the cadence once and revert it and Redis holds two live
  schedules — the old one nothing removed and the new one — each running a full-bucket listing and a
  full per-tenant fan-out onto a queue with concurrency 2. `upsertJobScheduler` is keyed on the id
  and overrides in place, which is the guarantee the old comment claimed. The unit test now models
  an upsert and makes `add` throw, so the mock cannot pass for the wrong reason.
- **The sweep is SCHEDULED, in `src/server/media/schedule.ts`.** A cleanup job that nothing
  enqueues is not periodic cleanup. `scheduleMediaCleanup()` registers `cleanup-orphans` on the
  media queue as a repeatable SystemJob at 04:00 Asia/Jerusalem — an hour after B1's lifecycle
  sweep, because that sweep is what purges an expired tenant and this one collects the prefix it
  leaves behind — under a stable `jobId`, so a worker restart replaces the schedule instead of
  stacking another daily full-bucket listing on top. The one call that activates it belongs to the
  worker bootstrap; see the sync point below.
- **Both scopes live in one module.** `src/server/queues.ts` registers processors by
  (queue, job name) and is a frozen shared file, so the `media/cleanup-orphans` entry has to serve
  both the SystemJob fan-out and the per-tenant sweep. The payload's own `scope` discriminant —
  the same one the dispatcher used to decide whether to hand us a transaction — picks the half.

## The library and alt text

- **Deleting an image a product still uses is refused by default**, naming how many products.
  `ProductImage` cascades from `Media`, so deleting anyway would silently strip the photo off a
  live product page: a merchant tidying their library would blank their own shop without being
  told. `force: true` is the explicit override.
- **Media objects are deleted one `delete(key)` at a time after the commit, never by prefix.**
  The media folder is a child of the tenant prefix, and a prefix delete built from a truncated
  string is how one wrong character removes an entire shop.
- **Alt text must contain Arabic**, enforced in `assertProductImageAlt()` and exported as
  `productImageAltSchema` so B2's product form and B3's pack import share one rule. `IMG_2043`
  passes "not empty" and helps neither a screen reader nor the shop's own search, and the
  accessibility floor (IS 5568 / WCAG 2.0 AA) is an Arabic-language surface.
- **"Arabic" means an Arabic LETTER, and the text is NFKC-normalised first.** Two corrections to one
  check. The old range began at U+0600, which swept in Arabic punctuation, the tatweel and the
  Arabic-Indic digits: `٢٠٢٤` passed as a product description, `ـــ` passed, and `IMG_2043،` passed
  — the exact Latin filename the rule exists to refuse, defeated by one Arabic comma. And without
  normalisation, text copied out of a PDF (a supplier's price list, which is where a shop owner
  actually gets product names) arrives as Arabic Presentation Forms: `ﻗﻤﻴﺺ` looks identical to
  `قميص` and is different codepoints, so the merchant was told to write in Arabic about text that
  was plainly Arabic in front of them, with no way to comply but to retype it. NFKC also means the
  STORED alt is the form a screen reader and the shop's own search expect. The intersection is
  expressed with two `u`-flag passes rather than `/[\p{Script=Arabic}&&\p{L}]/v`, because the `v`
  flag needs an ES2024 target and `tsconfig.json` is a forbidden shared file — a track must never
  loosen a build setting for every other track to shorten one line.
- **`listMedia`'s cursor is `{createdAt}|{id}`, and the sort is total.** `created_at` is not unique
  and is not close to unique here: a merchant multi-selecting photos fires the uploads in parallel,
  each ingest serialises on the tenant row and commits immediately after the one before it, so
  several rows share a millisecond routinely. A `createdAt < T` cursor skipped every row that TIED
  with the last row of the previous page — the photo is in the library, counted against
  `storage_mb`, and reachable from no page the merchant can scroll to.
- **`deleteMedia` LOCKS the row before it reads it.** The processor is a concurrent writer on that
  exact row and holds its lock for the seconds it spends in Sharp. Reading first meant deleting a
  «قيد المعالجة» tile read the pre-processing snapshot — `sizeBytes` still the upload, `variants`
  still empty — then blocked on the delete until the processor committed its own smaller size, six
  variant rows and a negative adjustment. The delete then released bytes that had already been
  released, and removed only the source key it had seen: the six variant objects the processor had
  just written were cascaded out of the database and left in the bucket with nothing to find them
  by.
- **`actor` and `ip` on `deleteMedia` are REQUIRED.** They defaulted to `SYSTEM_ACTOR` and null, so
  the obvious call — the shape the barrel advertises and every test used — produced an audit row
  saying the platform deleted a merchant's photo, from nowhere. A staff member wiping the library
  before they leave is exactly what an audit trail is for, and PHASES.md requires the ip to come
  from `getClientIp()`. Required moves the mistake from a silent misattribution to a typecheck
  failure in B2's screen. A forced delete also records the `productId`s it cascaded, since once
  those rows are gone nothing else can answer which product pages lost a photo.
- **`errors.inUse` no longer makes the count govern a noun.** «الصورة مستعملة في {count} منتج»
  is ungrammatical for every value it can render — «3 منتج» should be «3 منتجات», «2 منتج» should be
  «منتجين» — and the i18n layer has no plural helper yet. Rewording to «مستعملة في منتجات ({count})»
  is correct for all of them and costs nothing.
- **`storageUsage` reports 100% only when the account is actually full**, and pre-formats the
  remainder. `Math.round` turned 499.97MB of a 500MB plan into a full meter and copy saying the plan
  was exhausted, while the next upload was admitted normally. And `messages/ar/media.json` carries
  «المتبقي {remaining}» with nothing on the view to answer it — leaving B2 to format the one number
  on that panel itself, with `formatBytes()` (1GB = 1024MB) sitting next to `limitLabel` (1GB =
  1000MB), reproducing the exact self-contradicting sentence limits.ts was rewritten to eliminate.

## The endpoint

- **`/api/media/upload` establishes everything itself.** `/api/**` is unprefixed and answers on
  every hostname, so the handler reads the resolved surface (refusing a storefront hostname),
  takes the tenant from the SESSION and never from a header or a form field, and checks
  `checkMerchantAccess(..., 'media')` — `media` is a scope `staff` legitimately holds (Q13), so
  the question is not "is this an owner".
- **The plan-independent 25MB ceiling is enforced on the STREAM, not on `content-length`.** The
  declared-length check is kept as a cheap early refusal, but it cannot be the bound: a client
  chooses whether to declare a length, and `Transfer-Encoding: chunked` with none parses straight
  through the envelope. `request.formData()` would then materialise the whole payload — twice,
  once for the form and once for `arrayBuffer()` — before any limit ran, and nothing else caps it
  (the Caddyfile sets no `request_body max_size`, and the App Router applies no body limit to a
  Node-runtime route handler; `bodySizeLimit` covers server actions and the Pages API). One
  authenticated merchant or staff account could take the web container down with a single
  request. The body is now read through a counting reader that stops at the ceiling and cancels
  the stream, and the form is parsed from the bounded bytes.
- **An over-long alt text is `altTooLong`, everywhere.** It used to come back as `altTooShort` —
  «الوصف قصير. اكتب جملة توضّح شو ظاهر بالصورة» for a description that was too long, i.e. advice
  to write more of the thing that was refused. Three paths said it: `assertProductImageAlt`, the
  route's form parse, and `setMediaAltText`, whose `setAltTextSchema` carried its own
  `.min(1).max(300)` and therefore raised a raw English ZodError ("String must contain at most 300
  character(s)") BEFORE the Arabic rule ran. Every length rule now lives in `alt-text.ts` and
  comes back as a `MediaError` with an Arabic sentence and a code B2 can switch on.
- **Rate limiting degrades rather than failing closed.** Redis holds the shared counter; when it
  is unreachable — the normal state in development and in this repository's test suite — an
  in-process window still binds, weakly (N processes means N budgets). Failing closed would stop
  every merchant from uploading a product photo because a cache blinked. The fallback map is
  pruned and capped, so an outage cannot grow the heap without bound and never recover.
- **The counter and its TTL are ONE Lua script.** As `INCR` then `EXPIRE`, a connection that
  dropped between them left a key with no TTL — and no later call could repair it, because the
  `count === 1` branch that sets the expiry is never reached again. The counter then rose across
  days instead of resetting every minute, and once past the limit that tenant+IP was refused every
  upload from then on, permanently, with copy telling them to wait a minute. A single script makes
  the state unreachable rather than unlikely.
- **The slot is charged by the ROUTE, before the body is read.** It used to be charged inside
  `uploadMedia`, i.e. after the handler had already buffered up to 25MB — so a caller over its
  limit still cost the server the memory the limit exists to protect and could retry immediately at
  no cost to itself. A limit that only answers after paying that cost is not a limit. `/api/media/upload`
  is the only HTTP door; `ingestInternalImage` has no door and is deliberately not limited.
- **The limiter has tests now.** It had none: deleting the call entirely left the whole suite green,
  and "rate limiting via getClientIp()" was a spec bullet met by a line nobody checked. The tests
  pin the atomic TTL, the degraded path still binding, per-tenant and per-IP separation, and — the
  invariant-9 one — that a client cannot pick its own bucket with `X-Forwarded-For`.
- **Advisory metadata is truncated, never grounds for refusal.** `fileName` and
  `declaredContentType` are chosen entirely by the client and decide nothing. A `.max(255)` on them
  turned a perfectly good image with a long filename into a ZodError thrown before the magic-byte
  sniff or either plan check ran — a 500 and «صار خلل عندنا» for a picture that was fine.
- **`fail()` takes params, because one of the messages has a slot in it.** `altTooLong` renders
  «اختصره لـ {max} حرف أو أقل», and building it without params told the merchant to shorten their
  description to «{max}» characters — a placeholder shown to a human, which the language policy
  forbids. An Arabic-only assertion cannot see it (the rest of the sentence is Arabic either way),
  so every `MEDIA_ERROR_CODES` message is now also asserted to contain no unfilled `{slot}`.
- **A malformed `content-length` is not a verdict.** `Headers.get` joins duplicates into
  `"100, 100"` and `Number()` makes anything unparseable NaN; handing that to zod produced an issue
  on `contentLength`, which the handler read as "too large" — answering 413 «الملف أكبر من الحد
  الأقصى» to a 100-byte request and telling the merchant to shrink a photo that was never too big.
  An unusable header simply means the length is unknown; the stream ceiling is the real bound.
- **A client that hangs up is not a server error.** `reader.read()` rejecting on a closed socket
  propagated out of the handler as a 500, so every abandoned upload — routine on the 3G this
  platform's perf budget is written for — became an error-rate alert indistinguishable from a real
  fault.
- **`declaredContentType` is actually recorded now.** It was validated, threaded through the whole
  call chain and then dropped, while a comment promised it was kept for the support question it
  exists to answer. It is logged on the accepted path and, more usefully, on the magic-byte
  refusal — the moment where "the browser said it was a PNG" is the actual diagnostic.

## Which test assertions are driver-agnostic, and which are not

| Assertion | Where | Driver-agnostic? |
|---|---|---|
| `deleteByPrefix` removes every object under a tenant prefix | `a3-storage-local`, `a3-r2-driver`, integration | **Yes** — contract, checked against a real filesystem and against the S3 command stream |
| `delete(key)` removes exactly one object | same | **Yes** |
| `signedUrl` clamps the TTL | `a3-storage-local`, `a3-r2-driver` | **Yes** (the clamp); the URL FORMAT is not — local signs an HMAC, R2 presigns SigV4 |
| `signedUrl` resolves only its own key and stops at its TTL | `a3-storage-local` | **Local-specific mechanism**, same semantics. On R2 the equivalent is enforced by SigV4 itself, which cannot be exercised offline |
| `publicUrl` refuses a non-media key | both | **Yes** |
| `publicUrl` refuses when no CDN origin is configured | `a3-r2-driver` | **R2-only** — the local driver deliberately falls back to `/dev-media` |
| Encryption requested for `_exports/`, cache-control for media | `a3-r2-driver` | **R2-only** — the local driver ignores both options |
| Prefix listing pages, deletes batch at 1000 | `a3-r2-driver` | **R2-only** — an S3 protocol limit |
| Variants, counters, limits, magic bytes, orphan rules | integration | **Yes** — all of it goes through the `StorageAdapter` interface |

There is no R2 bucket and no network bucket in this environment, so the R2 driver is exercised
against an in-memory fake that answers the real command objects, with one exception:
`signedUrl` presigns for real, because SigV4 is arithmetic over the client's credentials and
needs no network. The clamp is therefore measured on an actual URL.

## Not built, deliberately

- **The media library SCREEN.** `src/app/dashboard/**` is B2's surface. Everything it needs is
  exported from `@/server/media`: `listMedia`, `deleteMedia`, `setMediaAltText`, `storageUsage`,
  `productImageAltSchema`, and the Arabic copy in `messages/ar/media.json`.
- **Anything touching `Subscription` or `Tenant.state`.** Invariant 5: lifecycle state changes
  live in `src/server/billing` and nowhere else. The pipeline reads the tenant row and writes one
  column of it (`storageBytesUsed`), which the schema comment assigns to the media jobs.

## Sync points for the main session

**1. One line in `src/worker/index.ts` to activate the orphan sweep.** The schedule is written and
tested (`scheduleMediaCleanup()`, `tests/unit/a3-cleanup-schedule.test.ts`); only the call is
outside this track's write scope. Inside `registerRepeatables()`, beside
`lifecycle/sweep-subscriptions`:

```ts
import { scheduleMediaCleanup } from '@/server/media/schedule';
// ...
await scheduleMediaCleanup();
```

Until that lands, the sweep exists but never runs: the source object of every failed or
rolled-back upload accumulates in R2, and the `_exports/` protection this module was written for
is never exercised in production.

**2. `DATABASE_URL_SYSTEM` must be set in the production environment.** It is `.optional()` in
`src/env.ts` and falls back to `DATABASE_URL`, and only `docker-compose.dev.yml` wires it — there
is no production compose file in the repository yet. With it unset, `withSystemTxn` runs as
app_web and every cross-tenant sweep in the platform is reading through the wrong role's grants.
A3's own sweep now refuses to delete anything in that state and logs at `error`, but that is a
backstop, not a fix, and the same variable is what B1's lifecycle sweep will depend on.
`.env.example`, `docker-compose*.yml` and `Dockerfile` are all forbidden files, so this cannot be
done from the worktree.

**3. RESTORED, and a merge blocker: `registerMediaStorage()` must be called at boot in BOTH
containers.** An earlier draft of this file withdrew this sync point, and that was wrong. The
reasoning it gave — that the worker was the primary victim, that `process-upload` and
`cleanup-orphans` resolving their own driver was the whole fix, and that anything else was
"a bug in `src/server/export`'s own bootstrap, and B1 owns that file" — is mistaken on every count.
`src/server/media/storage` is the ONLY module in the repository that may build an R2 adapter (the
lint rule and `tests/unit/a3-s3-containment.test.ts` both enforce it), so no other folder's
bootstrap can fix this no matter who owns it.

What actually happens today, verified by following the import graph: the only route whose bundle
reaches `@/server/media` is `/api/media/upload`. Every other consumer calls the bare `storage()`
from `@/server/storage` — `src/server/export/download.ts`, `src/server/export/index.ts`,
`src/server/export/processors/cleanup-self-serve.ts`, `src/server/billing/index.ts` — and that
function THROWS under `STORAGE_DRIVER=r2` when no adapter has been registered. So on a fresh web
container, a suspended merchant opening `app.{DOMAIN}/export/{token}` from the WhatsApp message
gets a 500 instead of their catalogue, unless someone happened to upload a photo through that same
process first. It works intermittently, which is worse than failing outright: the Q18 promise dies
for the one person it was written for, on the day their site went dark. The worker has the same
shape for the export and self-serve-cleanup jobs.

Two lines, both outside this track's write scope:

```ts
// src/worker/index.ts, at the top of the bootstrap
import { registerMediaStorage } from '@/server/media/storage';
registerMediaStorage();

// and the web equivalent — src/instrumentation.ts (Next runs it once per server start)
```

`registerMediaStorage()` is idempotent and does nothing unless `STORAGE_DRIVER=r2`, so a
development checkout is unaffected. Do not merge A3 without it.

**4. The CDN origin must be restricted to the `media/` segment — and today nothing enforces it.**
`publicUrl()` refuses to mint a URL for a non-media key, which stops OUR code handing an export to
a template, and that is all it stops. The documented way to put a CDN in front of R2 is to attach a
Cloudflare custom domain to the bucket, which publishes EVERY key on that host — including
`tenants/{id}/_exports/{subscriptionId}-{suspendedAt}.zip`, a suspended merchant's entire
catalogue, at a key B1 makes deterministic per suspension. Acceptance asks that an `_exports/`
object "is not fetchable through the CDN without a signature"; the orphan-sweep half of that is
tested and true, the CDN half is an unenforced deployment assumption. The fix belongs to whoever
provisions the bucket: either a Cloudflare rule rejecting anything that does not match
`^tenants/[^/]+/media/`, or — better, because it is structural rather than procedural — a separate
bucket for exports. Recording it here because A3 merges long before anyone provisions R2, and the
person who does will have no reason to suspect the requirement exists.

**5. Deleting a photo does not purge the edge.** Media is served with `max-age=86400,
stale-while-revalidate=604800` (see "Processing"), so a deleted image can still be served from the
CDN for up to a day, and B1's purge inherits the same window. That is a bounded, statable exposure
rather than the year the original `immutable` header implied, but the complete fix is a cache purge
on delete. The credentials already exist (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ZONE_ID`); what does
not exist is a decision about which zone fronts the bucket, and Phase 6's privacy copy needs to
match whatever is chosen.
