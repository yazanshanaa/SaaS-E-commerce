Give a deployment a door for its own site blocks, without opening the Caddyfile

The launch server already serves a static company site from an nginx that holds
ports 80 and 443. Caddy has to own those two: on-demand TLS for merchant custom
domains and the wildcard certificate can only be obtained by the process that
answers the ACME challenge, so leaving nginx in front and putting Caddy behind
it would quietly delete the feature the whole `on_demand_tls` block exists for.

The migration itself is small - nginx moves to an internal port and Caddy
reverse-proxies it, its own configuration untouched byte for byte. The part that
needed a decision was WHERE that site block lives.

Not in the Caddyfile. That file is platform code, shipped to every deployment,
and one machine's company hostname welded into it is a coupling that outlives
whoever added it. So the Caddyfile gains one `import` of a directory the compose
mounts, git-ignored except for a placeholder - Caddy refuses to start on an
import glob matching no files, and a stack that will not boot on a fresh
checkout because a directory is empty is a bad trade for two lines of comment.

The placeholder carries the itqantech.io block as a worked example and the
reasoning above, so the next person to stand a box up does not rediscover it.

Nothing here changes behaviour on a deployment that has no local blocks.
